# План реализации

`docs/roadmap.md` — **единственный источник правды по плану развития проекта**.

Все новые продуктовые идеи, технические задачи и изменения приоритетов сначала
добавляются сюда. GitHub Issues и PR используются для выполнения конкретных пунктов
roadmap и не должны становиться отдельным параллельным backlog.

**Основной домен проекта:** `vsegiri.com`.

## Архитектурное решение: статический production на Cloudflare

Для первой production-версии `vsegiri.com` используется **статический сайт на Cloudflare**,
без runtime-зависимости от Workers и D1. Публичные HTML-страницы заранее собираются из
данных репозитория и локальной SQLite-базы и затем целиком публикуются на Cloudflare.

Причина: архив обновляется редко (ориентир — около 10 новых протоколов в год), поэтому
пересборка статического сайта после изменения данных проще и надёжнее постоянного backend.
Статический HTML также хорошо подходит для SEO и индексации страниц спортсменов, персон,
соревнований и результатов.

На этапе MVP:

- источником данных остаются `data/*.json`, миграции, генераторы и git-история;
- SQLite используется во время сборки, но публичный сайт не зависит от постоянно работающей БД;
- production-раздача HTML и assets выполняется через Cloudflare Pages;
- production-деплой запускается GitHub Actions при push/merge в `main`: `npm run build` →
  `dist` → Wrangler → Cloudflare Pages;
- встроенная Git-интеграция Cloudflare Pages не используется как production CI/CD;
- GitHub Pages остаётся ручной резервной/preview-копией;
- Cloudflare Web Analytics включён для статистики посещений;
- Worker, D1 и R2 не являются обязательными компонентами production runtime.

При этом архитектура должна сохранять **прямой путь апгрейда** к динамической версии.
Если появится реальная необходимость в админке, авторизации, API, серверном поиске,
редактировании без полной пересборки или существенно более частом обновлении данных,
production можно перевести на **Cloudflare Workers + D1** (и R2 для файлов протоколов),
сохранив домен, публичные URL и существующую модель данных. Уже созданные прототипы
Worker/D1/R2 можно использовать как задел для такого перехода, но они не должны усложнять MVP.

Обозначения:

- ✅ выполнено;
- 🟡 выполнено частично / требует завершения;
- ⬜ не начато или ещё не доведено до требуемого результата.

Оценки в шкале документа требований: S — до дня, M — 1–3 дня, L — неделя и больше.

но не являются обязательной частью текущего production runtime.

## Шаг 4. Публикация — S — 🟡

Публичные турниры и результаты уже собираются и отображаются. Поддерживаются отложенные
категории (`is_deferred`).

Для MVP публикация означает полную статическую пересборку сайта после изменения данных и
автоматический deploy готового `dist` через GitHub Actions и Wrangler в Cloudflare Pages.
Отдельная постоянно работающая production-БД для этого не требуется.

Остаётся довести административный workflow публикации: публикация только без открытых
проблем (FR-A8), ручное редактирование (FR-A11), справочники списками (FR-A12).

Наполнение идёт параллельно развитию продукта.

## Правило ведения roadmap

1. Новая идея или задача сначала добавляется в этот файл.
2. Если задача достаточно конкретная для реализации, под неё можно открыть Issue/PR.
3. После merge соответствующий пункт roadmap сразу отмечается выполненным или обновляется.
4. Закрытые Issues не считаются историей плана: история плана живёт в git-истории этого
   файла.
5. `ERRATA.md` остаётся отдельным источником известных ошибок **в данных**, а не backlog
   разработки.
