# Импорт протокола

Источник может быть **PDF, Excel или изображение**. Формат влияет только на извлечение данных; после получения строк категории правила одинаковые.

## Главный принцип

**Источник является авторитетом для импортируемых значений.**

Не исправлять спортивную логику протокола и не подменять данные более «правдоподобными». Проверять нужно точность переноса и техническую целостность репозитория.

Сохранять как есть, если это действительно напечатано в источнике:

- необычный порядок мест и результатов;
- собственный вес, не совпадающий с ожиданиями по категории;
- отличающуюся дату/год рождения;
- ФИО, клуб или тренера с возможной опечаткой;
- необычный итог двоеборья;
- повтор одного имени.

Ошибка чтения/OCR/сдвига колонок — наша ошибка и должна быть исправлена. Странность исходного протокола — не причина менять данные.

Явная инструкция пользователя важнее дефолтов этого skill.

## 1. Работа в репозитории и параллельные агенты

В `girevoy-archive` другие агенты могут одновременно добавлять категории, менять workflow или персоны.

Обязательно:

1. Перед началом получить **свежий SHA целевой/default ветки**.
2. Создавать рабочую ветку только от этого SHA.
3. Перед записью category-fragment проверить, что такой файл не появился у другого агента.
4. Перед PR/merge снова получить свежий SHA целевой ветки и проверить mergeability/diff.
5. Никогда не делать force-update общей ветки и не откатывать чужие изменения.
6. Если другой агент изменил тот же файл, пересоздать/обновить свою ветку от свежей головы вместо слепого merge конфликта.

Если пользователь требует merge каждой категории для запуска deploy — выполнять. Иначе категории можно объединять в логичные пачки.

## 2. Быстрый обзор источника

Перед массовой записью определить индивидуальные категории, которые нужно импортировать.

По умолчанию **не импортировать как обычные результаты**:

- эстафеты;
- командный зачёт/командные очки;
- жонглирование;
- список судей;
- служебные таблицы и подписи.

Если пользователь отдельно просит один из этих разделов — обрабатывать отдельной задачей и только в подходящей модели данных.

## 3. Турнир и файлы

Проверить существующие `data/*.json` по названию, датам и городу. Если турнир уже существует — использовать его slug.

Предпочтительная структура массового импорта:

```text
data/<slug>.json
data/categories/<slug>/long-cycle-m-63.json
data/categories/<slug>/snatch-f-58.json
data/categories/<slug>/biathlon-m-63.json
```

Одна категория = один fragment-файл.

### Обязательный шаблон `source`

Для нового `data/<slug>.json` явно записывать технические поля, даже если часть значений неизвестна:

```json
{
  "source": {
    "filename": "protocol.xlsx",
    "page_count": null,
    "is_scan": false,
    "id_base": 37000
  }
}
```

Правила:

- `filename` — строка с именем исходного файла;
- `page_count` — целое число для PDF/известного количества страниц либо `null`; **не пропускать поле**;
- `is_scan` — явный boolean `true`/`false`; **не пропускать поле**;
- `id_base` — уникальная свободная база ID, не пересекающаяся с другими турнирами;
- дополнительные поля (`names_without_middle`, `birth_precision`, `note`) добавлять по необходимости.

Перед commit нового турнира проверить, что `source` можно безопасно читать как через `src[...]`, так и через `src.get(...)`; новые необязательные поля в генераторах должны читаться через безопасный default, чтобы отсутствие метаданных старых турниров не ломало сборку.

## 4. Подключение нового турнира к Pages

Наличие JSON и category-fragments недостаточно. Новый турнир должен участвовать в сборке.

Проверить `.github/workflows/pages.yml`:

1. Есть строка генерации:

```sh
python3 scripts/gen_seed.py data/<slug>.json > .local/<slug>.sql
```

2. `.local/<slug>.sql` включён в `cat ... | sqlite3 .local/girevoy.db`.

3. Турнир не добавлен дважды и имя файла/slug совпадают во всех местах.

После изменения workflow проверить diff целиком, чтобы не удалить строки турниров, добавленные параллельным агентом.

## 5. Предварительная идентификация спортсменов — обязательна

`raw_name` и дата/год рождения сохраняются **ровно по текущему источнику**. Проверка
идентичности не переписывает сырой протокол.

Если источник содержит только имя без отчества или только год рождения, можно добавить:

```json
{
  "names_without_middle": true,
  "birth_precision": "year"
}
```

Перед финализацией JSON/PR для **каждого нового упоминания спортсмена** проверить, нет ли
этого человека уже в базе. Для поиска и принятия решения использовать критерии из
`person-audit`, а не только точное строковое совпадение:

- одинаковые фамилия + имя + год рождения;
- одинаковое полное ФИО;
- фамилия + имя совпадают, а в одном источнике отсутствует отчество;
- различается только формат даты/года рождения;
- близкие варианты ФИО с возможной опечаткой при совпадающих дополнительных признаках:
  год рождения, регион, клуб, тренер, история выступлений;
- проверять и отрицательные признаки: одновременное участие как разных людей в одной
  категории, устойчиво разные годы рождения и другие несовместимые факты.

Кандидата классифицировать теми же статусами, что и `person-audit`:
`SAFE_MERGE`, `REVIEW`, `KEEP_SEPARATE`, `INSUFFICIENT_DATA`.

**Никаких автоматических merge.** Все найденные `SAFE_MERGE` и `REVIEW` показать
пользователю **до финализации импорта** с конкретным основанием и ссылкой/указанием на
существующую запись. Только после решения пользователя:

- подтверждённое совпадение оформить существующим механизмом merge персон;
- подтверждённо разных людей оставить раздельными;
- при недостатке данных не объединять.

Если подходящих кандидатов нет, импорт продолжается без дополнительного согласования.
Более полную существующую персону не затирать более бедным вариантом имени.

### Нормализация областей при сопоставлении

Различие только в сокращении типа региона не считается ошибкой и не является конфликтом
идентичности.

Пример:

- `Томская обл.` = `Томская область` → каноническое значение для сравнения:
  `Томская область`.

То же правило применять ко **всем областям России**: формы вида
`<Название> обл.`, `<Название> обл` и `<Название> область` считать одним регионом
при поиске существующего спортсмена/тренера. Разницу в точке, регистре и лишних пробелах
также игнорировать для сопоставления.

Это **не ERRATA и не ошибка протокола**. `raw_region` всегда сохранять так, как он
напечатан в источнике; нормализованную форму использовать только для поиска и сравнения.
Не объединять действительно разные субъекты РФ только из-за похожего названия.

## 6. Извлечение по формату

### PDF

Если PDF текстовый — извлекать текст/таблицы напрямую. Если скан — использовать `scripts/ocr_pdf.py` или чтение изображения страницы.

`page` результата сохранять, если номер страницы известен; иначе `null`.

Для OCR проверять только возможные ошибки чтения: поворот, десятичные разделители, `0/O`, `1/I`, похожие цифры, сдвиг столбцов.

### Excel

Учитывать:

- merged cells;
- разницу между пустой ячейкой, `0` и прочерком;
- даты как даты;
- дробный собственный вес без потери точности;
- служебные строки не превращать в спортсменов.

### Изображение

Если символ/число неоднозначно — пересмотреть конкретное место. Не выбирать значение по спортивной правдоподобности.

## 7. Категория и модель результата

Базовое соответствие:

| В источнике | JSON |
| :- | :- |
| Толчок | `discipline: "jerk"` |
| Рывок | `discipline: "snatch"` |
| Толчок по длинному циклу | `discipline: "long_cycle"` |
| Двоеборье | `discipline: "biathlon"` |
| Вес гирь | `bell_kg` |
| Регламент времени | `time_limit_min` |
| Одной/двумя руками | `hands` |
| Весовая категория | `weight_class` |

`weight_class` хранить без `кг`, например `"63"`, `"95+"`.

- `jerk`, `snatch`, `long_cycle` — основной результат как количество повторений;
- `biathlon` — итоговые очки как `points`, компоненты отдельно по модели проекта;
- неизвестную систему подсчёта не подгонять под неподходящее поле.

Если текущая схема не позволяет сохранить смысл без потерь — использовать `schema-change`, а не придумывать несовместимый JSON.

## 8. Строки категории

Базовый порядок полей задаётся `columns`, например:

```text
["place", "name", "born", "rank", "region", "club",
 "body_weight_kg", "reps", "rank_achieved", "team_points", "coach"]
```

`region`, `club`, `name`, `born`, `coach` сохранять максимально близко к источнику. Прочерк не заменять выдуманным значением.

`region` сохраняется как в источнике, но нормализуется справочником: каждое написание
обязано быть в `data/regions.json`, иначе `gen_seed.py` падает с
`неизвестный регион ...`. Новое написание — добавить алиас к существующему субъекту
(не заводить новый регион ради «обл.» вместо «область») и пересобрать справочник
через `npm run regions:gen`.

Если командные очки не импортируются — не использовать их как спортивный результат.

## 9. DNS / DNF / DSQ

Участник без числового результата не должен исчезать и не должен получать выдуманный `0`.

Если источник содержит `DNS`, `DNF`, `DSQ`, `снят врачом` и т.п., сохранить статус в поддерживаемой схемой форме. Если схема не умеет это представить — использовать `schema-change`.

## 10. Тренеры и персоны

`coach` в JSON — сырой текст протокола. Не исправлять и не «улучшать» его при импорте.

До финализации импорта для **каждого распознанного тренера** проверить, существует ли он
уже в базе. Использовать те же правила идентичности из `person-audit`, включая поиск
этого человека в других ролях — спортсмена, судьи или спортивного деятеля.

Для тренеров особенно важно:

- варианты форматирования `Иванов И.И.` / `Иванов И. И.` считать кандидатами на одну
  персону, но не доказательством сами по себе;
- одинаковые фамилия и инициалы без дополнительных признаков не сливать автоматически;
- полное ФИО, связанные спортсмены, регион, клуб, соревнования и другие роли использовать
  как подтверждающие признаки;
- если в одной raw-строке перечислено несколько тренеров, сначала корректно разделить их
  по действующим правилам генератора, а затем сопоставлять каждого отдельно;
- нормализацию `обл.` ↔ `область` применять так же, как для спортсменов.

Все `SAFE_MERGE` и `REVIEW` по тренерам показать пользователю **до финализации
импорта**. Автоматически объединять тренеров нельзя.

`gen_people.py` строит производные связи. Подтверждённые merge/split правил персон
хранятся отдельно (`data/person_merges.json` и связанные структуры) и не переписывают
raw-текст протокола.

Не добавлять хрупкие тесты, которые требуют существования исторической персоны только
потому, что она упомянута в старом merge/split-правиле. Тест должен проверять
преобразование правила на релевантном входе или реальные сущности текущего набора данных.

## 11. Обязательные технические проверки

Эти проверки обязательны именно для предотвращения поломок сборки. Они не проверяют спортивную правдоподобность протокола.

### Для каждой изменённой JSON-категории

- JSON парсится;
- структура `columns` соответствует `rows`;
- числовые поля имеют тип, ожидаемый текущим генератором;
- target fragment не дублирует уже существующий fragment.

### Для нового/изменённого турнира

Обязательно выполнить генератор конкретного турнира:

```sh
mkdir -p .local
python3 scripts/gen_seed.py data/<slug>.json > .local/<slug>.sql
```

Команда должна завершиться с кодом 0. Нельзя считать импорт готовым только потому, что JSON валиден.

После этого проверить генератор персон:

```sh
python3 scripts/gen_people.py > .local/people.sql
```

### Перед merge пачки импорта

Если доступна локальная среда, воспроизвести релевантную часть `.github/workflows/pages.yml`:

1. сгенерировать SQL всех подключённых турниров;
2. собрать `.local/girevoy.db` через migrations/seeds/generated SQL;
3. выполнить:

```sh
node --test tests/*.test.mjs
node scripts/snapshot.mjs .local/girevoy.db dist
```

4. проверить наличие основных страниц (`dist/index.html`, `results.html`, `coaches.html`, страницы `c-*`, `a-*`, `p-*`).

Если локальный запуск невозможен, это не повод угадывать: после merge проверить GitHub Actions. При известном красном Pages build **не продолжать массово мержить следующие категории**, пока причина не найдена и не исправлена.

## 12. Проверка GitHub Actions после merge

После merge в ветку, на которую настроен Pages:

1. Найти workflow run именно для нового head SHA.
2. Проверить не только общий `success/failure`, но и шаги:
   - `Собрать базу со схемой, справочниками и данными протоколов`;
   - `Проверить персоны`;
   - `Отрендерить страницы`;
   - `Проверить, что страницы собрались`.
3. Если build упал — открыть лог **первого реально упавшего шага** и исправлять root cause, а не симптомы следующего шага.
4. Перед исправлением снова получить свежую голову ветки: другой агент мог уже внести изменение.
5. После фикса убедиться, что новый run относится к commit с исправлением.

Не утверждать, что deploy успешен, пока workflow не завершился `success`.

## 13. Что НЕ делать блокирующей проверкой

Не блокировать импорт из-за:

- порядка мест относительно результата;
- собственного веса относительно категории;
- повторов спортсмена;
- отличий ФИО/даты рождения между протоколами;
- возможных опечаток составителя;
- спортивной правдоподобности результата;
- пересчёта формулы двоеборья;
- самого факта наличия кандидата на дубль персон/тренеров.

Кандидат на дубль — не ошибка исходного протокола, но это обязательная **точка review
идентичности**: `SAFE_MERGE` и `REVIEW` должны быть показаны пользователю до
финализации импорта.

Исключение для спортивных/технических проверок — признаки **нашей** ошибки переноса: OCR,
тип поля, смещение колонок, неправильный fragment, сломанный JSON/SQL/генератор.

## 14. Цикл массового импорта

Для каждой категории:

1. Прочитать шапку и строки.
2. Сверить неоднозначные места чтения.
3. Проверить свежую ветку/наличие fragment у параллельных агентов.
4. Сопоставить входящих спортсменов и тренеров с существующей базой по правилам
   `person-audit`, включая нормализацию `обл.` ↔ `область`.
5. Показать пользователю все `SAFE_MERGE` и `REVIEW` и применить его решения через
   существующий механизм персон; raw-значения источника не менять.
6. Создать/обновить fragment JSON.
7. Проверить JSON и типы.
8. Для первого fragment нового турнира проверить metadata + подключение к workflow +
   `gen_seed.py`.
9. Commit/PR/merge — по инструкции пользователя или логичной пачкой.
10. Если merge запускает Pages, учитывать результат последнего run до продолжения после
    известной ошибки.

## 15. Progress/status

На вопрос пользователя о статусе всегда сверять ответ с актуальным GitHub состоянием, а не с локальным планом:

- свежий SHA целевой ветки;
- какие category-fragments уже реально присутствуют;
- открытые/смёрженные PR;
- последний Pages run и первый упавший шаг, если есть.

Не выдавать старый run за текущий при параллельных commit/merge.
