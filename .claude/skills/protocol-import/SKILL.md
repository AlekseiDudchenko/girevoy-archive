# Импорт протокола

Этот skill — **оркестратор импорта**, а не справочник по всем моделям проекта.

Он отвечает за последовательность работы и обязательные контрольные точки. Детальные правила
по смежным задачам живут в отдельных skills:

- `person-audit` — идентичность спортсменов, тренеров и других персон, дубли и merge;
- `protocol-errors` — подтверждённые ошибки первоисточника, corrections и ERRATA;
- `schema-change` — случаи, когда текущая модель данных не может без потерь представить
  значение из протокола.

Не копировать сюда алгоритмы этих skills. При возникновении соответствующего случая
переходить к ним.

## Главные гарантии импорта

Готовый импорт должен обеспечивать одновременно:

1. **Сохранность источника.** Оригинальный файл и raw-значения не теряются.
2. **Полноту.** Каждая индивидуальная категория и каждая строка источника либо импортирована,
   либо явно отмечена как пропущенная с причиной.
3. **Отсутствие тихих исправлений.** Ошибка источника не маскируется под обычный импорт.
4. **Контроль идентичности.** Новые упоминания спортсменов и тренеров проверены через
   `person-audit`.
5. **Контроль справочников.** Регион не создаётся молча из нового написания.
6. **Техническую воспроизводимость.** Canonical static build проходит целиком.
7. **Проверяемый PR.** До merge есть стандартный import report и зелёный PR build.

## Главный принцип данных

**Источник является авторитетом для того, что в нём напечатано.**

Не менять значение только потому, что оно выглядит спортивно неправдоподобным.

Если в источнике действительно напечатаны:

- необычный результат;
- странный порядок мест;
- неожиданный собственный вес;
- отличающийся год рождения;
- опечатка в ФИО;
- необычный регион/клуб;
- повтор одного имени;
- неожиданный вес гири,

сначала сохранять факт источника и классифицировать ситуацию.

Различать три типа проблем:

### Import error

Мы неправильно прочитали источник: OCR, сдвиг колонки, неверный тип, пропущенная строка,
ошибка парсинга.

Исправить импорт. Это **не** ERRATA первоисточника.

### Source anomaly / source error

Значение именно так напечатано в первоисточнике, но есть основания считать его ошибочным.

Не исправлять молча. Использовать `protocol-errors`.

### Identity review

Сырое ФИО похоже на существующую персону или конфликтует с ней.

Не менять raw-значение. Использовать `person-audit`.

# GATE 0 — Fresh repository state

До чтения/записи данных:

1. Прочитать релевантную часть `docs/roadmap.md`.
2. Получить свежий SHA `main`.
3. Создать отдельную ветку от этого SHA.
4. Проверить открытые PR, которые могут добавлять тот же турнир, источник, категории,
   регионы или правила персон.
5. Не коммитить напрямую в `main`.
6. Не откатывать изменения других агентов.

Если параллельный агент уже создал нужный fragment или изменил тот же файл, сначала
синхронизировать состояние, а не создавать вторую версию.

**Gate пройден, когда рабочая ветка основана на актуальном состоянии и нет скрытого
конфликта с параллельной работой.**

# GATE 1 — Source verified and preserved

До массового извлечения установить provenance.

## 1.1. Найти первоисточник

Предпочтение:

1. официальный файл федерации/организатора;
2. файл, предоставленный пользователем;
3. другая архивная копия с явно зафиксированным происхождением.

Если известен официальный URL, сохранить его в `competition.source_url`.

## 1.2. Архивировать оригинал

Следовать `sources/README.md`:

- оригинал хранить в `sources/<year>/`;
- бинарный файл после добавления не редактировать;
- обновить/проверить `sources/manifest.json`;
- если удалённый файл изменился, не перезаписывать старую редакцию — сохранить новую
  отдельно;
- `source.filename` по возможности должен совпадать с именем архивной копии.

Если пользователь прислал файл и найден официальный файл того же протокола, по возможности
сверить их размер/хэш или иным надёжным способом подтвердить, что это одна редакция.

## 1.3. Проверить существующий турнир

Искать по:

- названию;
- датам;
- городу;
- уровню;
- официальному URL;
- архивному имени файла.

Если турнир уже существует, использовать существующий slug и обновлять его, а не создавать
дубликат.

## 1.4. Source metadata

Для нового турнира минимум:

```json
{
  "source": {
    "filename": "protocol.xlsx",
    "page_count": null,
    "is_scan": false,
    "id_base": 37000
  }
}
```

Правила:

- `filename` — имя сохранённого источника;
- `page_count` — число страниц PDF либо `null`;
- `is_scan` — явный boolean;
- `id_base` — свободный диапазон, не пересекающийся с другими турнирами;
- `names_without_middle`, `birth_precision`, `note` — только если они реально
  описывают весь источник.

**Gate пройден, когда источник можно однозначно идентифицировать и воспроизвести.**

# GATE 2 — Protocol inventory complete

До создания category fragments построить **карту протокола**.

## 2.1. Excel

Перечислить все содержательные листы.

## 2.2. PDF / scan

Перечислить все найденные секции/таблицы/категории с номерами страниц.

## 2.3. Inventory table

Для каждого раздела определить:

```text
source section | discipline | sex | weight class | bell kg | rows | action | reason
```

Пример:

```text
ДВ 63       | biathlon   | m | 63  | 32 | 11 | IMPORT |
ДЦЖ 63      | long_cycle | f | 63  | 24 |  8 | IMPORT |
Эстафета М  | relay      | m | —   | 32 |  5 | SKIP   | relay not modeled as individual results
Судьи       | —          | — | —   | —  | 24 | SKIP   | service table
```

По умолчанию не импортировать как обычные индивидуальные результаты:

- эстафеты;
- командный зачёт и командные итоговые таблицы;
- жонглирование;
- списки судей;
- служебные таблицы и подписи.

Не пропускать раздел молча. У каждого `SKIP` должна быть причина.

## 2.4. Зафиксировать ожидаемые totals

До импорта знать:

- число найденных индивидуальных категорий;
- ожидаемое число импортируемых категорий;
- число явно пропускаемых разделов;
- ожидаемое число строк индивидуальных результатов.

**Gate пройден, когда ни один лист/раздел источника не остаётся с неизвестным статусом.**

# GATE 3 — Extraction reconciled

Извлекать данные без спортивных догадок.

## 3.1. Общие правила

Сохранять raw-значения максимально близко к источнику:

- имя;
- год/дату рождения;
- регион;
- клуб;
- тренера;
- числовые значения;
- статус участника.

Не превращать прочерк в выдуманное значение.

Не превращать отсутствие результата в `0`.

## 3.2. PDF

Если PDF текстовый — извлекать текст/таблицы напрямую.

Если скан — использовать существующий OCR/визуальную проверку. Для неоднозначного места
проверять сам фрагмент страницы, а не выбирать наиболее правдоподобное спортивное значение.

Сохранять номер страницы, если он известен.

## 3.3. Excel

Обязательно учитывать:

- merged cells;
- скрытые/служебные строки;
- пустая ячейка vs `0` vs прочерк;
- Excel dates;
- дробные значения веса;
- переносы строк внутри ячеек;
- формулы и отображаемые значения;
- перестановку или нестандартный смысл колонок на отдельных строках.

## 3.4. Изображение

При неоднозначном символе пересмотреть конкретное место. Не восстанавливать число по
контексту соревнований.

## 3.5. DNS / DNF / DSQ / medical withdrawal

Участник не должен исчезать из-за отсутствия числового результата.

Если источник содержит статус вроде:

- DNS;
- DNF;
- DSQ;
- `снят врачом`;
- другой явно напечатанный статус,

сохранить участника и статус через поддерживаемую модель. Если текущая схема не умеет это
представить — перейти к `schema-change`.

## 3.6. Row reconciliation

Для каждой импортируемой категории должно выполняться:

```text
source individual rows
=
imported rows
+ explicitly excluded rows
```

Любое расхождение — STOP до объяснения.

**Gate пройден, когда каждая строка источника учтена.**

# GATE 4 — Category semantics reviewed

После извлечения, но до финализации JSON, проверить метаданные каждой категории.

Базовые поля:

```text
discipline
sex
weight_class
bell_kg
hands
time_limit_min
norms
source_sheet/page
rows count
```

Базовое отображение:

| В источнике | JSON |
| :- | :- |
| Толчок | `jerk` |
| Рывок | `snatch` |
| Толчок по длинному циклу | `long_cycle` |
| Двоеборье | `biathlon` |
| Вес гири | `bell_kg` |
| Регламент времени | `time_limit_min` |
| Одной/двумя руками | `hands` |
| Весовая категория | `weight_class` |

`weight_class` хранить без `кг`, например `"63"`, `"95+"`.

## 4.1. Модель спортивного результата

Использовать текущую модель проекта, не подменяя одно поле другим:

- `jerk`, `snatch`, `long_cycle` — основной числовой результат хранится как количество
  повторений (`reps`);
- `biathlon` — итог хранится как очки (`points`), а компоненты толчка/рывка — отдельно
  по действующей схеме;
- `team_points` — командные очки, а не индивидуальный спортивный результат;
- участника без числового результата не превращать в `0`;
- неизвестную формулу/систему подсчёта не подгонять под ближайшее существующее поле.

Если модель результата неизвестна или теряет смысл данных — `schema-change`.

## 4.2. Semantic anomaly review


Это **review, а не автоматическая коррекция**.

Флагать ситуации вроде:

- один женский лист содержит 32 кг, соседние аналогичные листы — 24 кг;
- одна весовая категория выбивается из последовательности;
- только один лист имеет другой `hands` или `time_limit_min`;
- нормы не соответствуют соседним категориям по структуре;
- одинаково названные секции по-разному интерпретированы;
- заголовок и содержимое таблицы противоречат друг другу.

Если аномалия реально напечатана в источнике, сохранить факт и при необходимости перейти
к `protocol-errors`. Не исправлять на основании одной только правдоподобности.

**Gate пройден, когда каждая аномалия либо объяснена, либо вынесена в review/correction.**

# GATE 5 — Regions and row semantics resolved

## 5.1. Region

`raw_region` сохранять как напечатано.

Нормализованное значение должно разрешаться **только через `data/regions.json`**.

Если написание неизвестно:

1. не создавать новый субъект автоматически;
2. определить, является ли это вариантом существующего региона;
3. если да — добавить alias;
4. пересобрать справочник через `npm run regions:gen`;
5. если значение неоднозначно — STOP/REVIEW.

Формы вроде `Томская обл.` и `Томская область` — alias одного субъекта, а не два
региона и не ERRATA.

## 5.2. Region ↔ club sanity check

Отдельно флагать строки, где:

- значение `region` выглядит как известный клуб/общество;
- значение `club` разрешается как известный регион;
- только одна строка листа имеет обратный порядок колонок;
- составной регион неожиданно распался по `/`, `\\`, запятой или дефису.

Не переставлять поля автоматически. Сначала сверить исходную строку.

Если в самом источнике колонки переставлены — raw значения сохранить, а исправление
нормализованного смысла оформить через `protocol-errors`.

## 5.3. Club

Сохранять raw club. Не создавать ложную нормализацию только ради прохождения генератора.
Если требуется новая модель alias клубов — это отдельная задача/ `schema-change`.

**Gate пройден, когда ни один импортированный raw region не остаётся неразрешённым и
подозрительные перестановки region/club проверены.**

# GATE 6 — People reviewed through person-audit

Не реализовывать здесь собственный fuzzy matching.

После получения строк собрать все новые упоминания:

- спортсменов;
- тренеров;
- при наличии — людей в других ролях.

Перед финализацией импорта проверить их через правила `person-audit`.

Минимально ожидаемые исходы:

- существующая персона найдена без конфликта;
- новая персона;
- `SAFE_MERGE`;
- `REVIEW`;
- `KEEP_SEPARATE`;
- `INSUFFICIENT_DATA`.

Все `SAFE_MERGE` и `REVIEW` показать пользователю **до применения merge**.

Raw ФИО текущего протокола не переписывать ради канонического имени.

Подтверждённые merge оформлять только способом, описанным в `person-audit`.

## 6.1. Post-generation sanity check

После `gen_people.py` проверить **дельту новых сущностей**, а не только успешный exit code.

Показать как минимум:

```text
new athletes
new people
new coaches
new regions
new clubs (если применимо)
```

Отдельно искать подозрительные новые имена:

- одна буква или один инициал, например `А.`;
- инициалы без фамилии;
- склеенное `АбдуллинР.Р.`;
- запятая внутри инициалов, которая могла стать разделителем тренеров;
- несколько тренеров, ошибочно объединённых в одного;
- один тренер, ошибочно разделённый на несколько;
- необычные пробелы/пунктуация, породившие отдельную персону.

Если обнаружена такая сущность — STOP и исправить parser/данные до PR.

**Gate пройден, когда person review завершён и генерация не создаёт очевидный мусор.**

# GATE 7 — Fragments and tournament data finalized

Предпочтительная структура:

```text
data/<slug>.json
data/categories/<slug>/long-cycle-m-63.json
data/categories/<slug>/snatch-f-58.json
data/categories/<slug>/biathlon-m-63.json
```

Одна категория = один fragment.

Перед созданием fragment повторно проверить, что другой агент не добавил тот же файл.

Для каждой изменённой категории проверить:

- JSON парсится;
- `columns` соответствует структуре `rows`;
- типы числовых полей ожидаемы генератором;
- fragment не дублирует существующую категорию;
- `source_sheet` / `page` соответствует inventory;
- число строк совпадает с inventory;
- status rows не потеряны.

Не редактировать производный SQL вручную.

**Gate пройден, когда inventory и JSON взаимно однозначно соответствуют друг другу.**

# GATE 8 — Completeness audit

Перед build повторно свести весь турнир.

Обязательные инварианты:

```text
discovered individual categories
=
imported categories
+ explicitly skipped individual categories
```

и:

```text
source individual rows
=
imported results
+ explicitly skipped individual rows
```

Для служебных разделов отдельно показать число `SKIP`.

Проверить, что:

- ни один лист/раздел не потерян;
- одна категория не импортирована дважды;
- один и тот же спортсмен не исчез из-за пустого результата;
- после fragments итоговое число строк не изменилось случайно;
- source totals и generated totals объяснимо соотносятся.

Нельзя считать импорт полным только потому, что JSON валиден и `gen_seed.py` отработал.

**Gate пройден, когда расхождение totals = 0 либо каждое расхождение объяснено.**

# GATE 9 — Canonical static build green

Текущий production-путь — canonical static build, а не ручное перечисление шагов
`pages.yml`.

## 9.1. Подключение турнира

Новый турнир должен реально входить в canonical build.

Проверить текущую реализацию `scripts/build-static.sh` и используемый для турнира генератор.

Не предполагать, что достаточно добавить `data/*.json`: если build manifest сейчас
ведётся явно, турнир нужно включить туда.

Не редактировать `.github/workflows/pages.yml` ради каждого нового турнира:
GitHub Pages — резервная сборка и запускает общий `npm run build`.

Production/PR preview использует `.github/workflows/cloudflare-pages.yml`.

## 9.2. Локальная проверка

Обязательная финальная команда:

```sh
npm run build
```

Она должна завершиться успешно.

Дополнительно проверить релевантные инварианты БД, если они не покрыты build:

```sql
PRAGMA foreign_key_check;
```

Если менялись регионы, персоны, merges или corrections — выполнить дополнительные
проверки соответствующего skill.

## 9.3. Не лечить build обходом

Если build падает:

1. найти первый реально упавший этап;
2. исправить root cause;
3. не удалять данные и не ослаблять проверку только ради green build;
4. не продолжать массовые merge следующих импортов при известной поломке общей сборки.

**Gate пройден, когда полный production-equivalent build проходит на ветке.**

# GATE 10 — Standard import report

До PR/merge сформировать один и тот же краткий отчёт.

Шаблон:

```text
Competition: <name>

Source
- official URL: <url / none>
- archived file: <path>
- source verified: YES/NO

Inventory
- sections found: N
- individual categories found: N
- categories imported: N
- sections/categories skipped: N
  - <section>: <reason>

Rows
- source individual rows: N
- imported results: N
- explicitly skipped rows: N
- reconciliation delta: 0

Semantics
- category anomalies reviewed: N
- source errors/corrections: N
- import errors remaining: 0

Regions
- aliases added: N
- unresolved raw regions: 0

People
- existing matches: N
- new athletes: N
- new coaches: N
- SAFE_MERGE: N
- REVIEW: N
- suspicious generated people: 0

Build
- npm run build: PASS
- foreign_key_check: PASS/not separately required

Decision required
- <only unresolved review items>
```

Если `reconciliation delta != 0`, `unresolved raw regions != 0`,
`suspicious generated people != 0` или остаётся необъяснённая semantic anomaly —
импорт не готов к merge.

Следовать repository Git workflow:

```text
branch
  ↓
import + checks
  ↓
PR
  ↓
diff review
  ↓
CI / Cloudflare PR preview green
  ↓
merge
```

Перед PR:

1. получить свежий SHA `main`;
2. убедиться, что branch не содержит случайных чужих изменений;
3. проверить diff целиком;
4. убедиться, что import report соответствует реальному diff.

После открытия PR:

1. проверить workflow именно для head SHA;
2. для Cloudflare workflow убедиться, что `Build and test static site` прошёл;
3. если создан PR preview — использовать его для проверки затронутых публичных страниц;
4. не считать старый workflow run доказательством для нового commit.

Перед merge:

1. снова проверить актуальную голову `main`;
2. проверить mergeability;
3. убедиться, что все review-items решены;
4. убедиться, что CI относится к текущему head SHA;
5. не merge с красным CI.

После merge проверить production workflow для merge SHA, если изменение влияет на
публикуемый сайт.

# Массовый импорт нескольких турниров

При серии импортов не смешивать контроль полноты разных источников.

Для каждого турнира отдельно иметь:

- source provenance;
- inventory;
- row reconciliation;
- people review;
- import report.

Можно объединять несколько турниров в один PR, только если:

- каждый независимо прошёл Gates 1–10;
- diff остаётся обозримым;
- ошибка одного турнира не маскирует другой.

При обнаружении системной ошибки parser/generator сначала исправить её и получить green
build, затем продолжать серию.

---

# Когда нужно остановиться и вынести решение пользователю

Обязательный review пользователя нужен, если:

- `person-audit` дал `SAFE_MERGE` или `REVIEW`;
- непонятно, являются ли две секции одной категорией;
- source anomaly требует решения, применять ли correction;
- region/club невозможно однозначно интерпретировать;
- источник имеет несколько редакций и неясно, какая должна быть основной;
- текущая схема не может сохранить смысл данных без потерь.

Не задавать вопрос из-за обычной технической работы, которую можно надёжно выполнить
по существующим правилам.

---

# Что нельзя делать

Нельзя:

- импортировать результаты без предварительного inventory;
- считать импорт полным без row/category reconciliation;
- молча исправлять source value на «правильное»;
- создавать новый регион из неизвестной строки без проверки alias;
- автоматически merge персон только по похожему ФИО;
- копировать алгоритм `person-audit` внутрь этого skill;
- копировать workflow corrections из `protocol-errors`;
- удалять DNS/DNF/DSQ участника из-за отсутствия результата;
- вручную править generated SQL;
- считать успешный `gen_seed.py` достаточной проверкой;
- забывать включить новый турнир в canonical static build;
- редактировать `pages.yml` как список турниров;
- открывать/merge PR при необъяснённой разнице totals;
- продолжать массовый импорт при известном красном build;
- коммитить напрямую в `main`.

# Status requests

Если пользователь спрашивает статус импорта, отвечать по актуальному GitHub состоянию,
а не по памяти агента.

Проверять:

- свежий SHA `main`;
- наличие source/archive;
- какие category fragments реально находятся в ветке/main;
- открытый/merged PR;
- текущий head SHA PR;
- CI/Cloudflare run именно для этого SHA;
- unresolved items из import report.

Короткий статус должен различать:

```text
EXTRACTING
REVIEW_REQUIRED
READY_FOR_PR
PR_OPEN
CI_FAILED
READY_TO_MERGE
MERGED
DEPLOYED
```

Не писать `DEPLOYED`, пока production workflow для соответствующего merge SHA не
завершился успешно.
