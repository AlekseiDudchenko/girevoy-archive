# Импорт протокола

Источник может быть **PDF, Excel или изображение**. Формат меняет только этап извлечения;
после получения строк категории правила одинаковые.

Данные настоящие. Не исправлять их догадкой и не «нормализовать» исходник молча.
Странное, но подтверждённое значение сохраняется как в протоколе и фиксируется в
`ERRATA.md`. Ошибка извлечения исправляется в JSON; если она уже попала в историю,
зафиксировать исправление явно.

Явные инструкции администратора важнее дефолтов skill. Например, если сказано
«эстафеты и командные очки игнорируй», их не добавлять даже в `deferred`.

## 1. До первого коммита: inventory всего источника

Перед записью данных сначала полностью перечислить содержимое источника.

Для Excel — все листы и все таблицы на них. Для PDF — все страницы/разделы. Для набора
изображений — все изображения/страницы.

Составить рабочий manifest со статусом каждого раздела:

```text
ДЦ М 63   IMPORT
ДЦ М 68   IMPORT
Р Ж 58    IMPORT
Эстафета  IGNORE
Жонглирование UNSUPPORTED
Командный зачёт IGNORE
```

Допустимые статусы:

- `IMPORT` — индивидуальная категория, которую нужно внести;
- `IGNORE` — администратор явно сказал не импортировать;
- `UNSUPPORTED` — данные есть, но текущая схема архива их не представляет корректно;
- `DEFERRED` — только если администратор явно просит отложить на потом.

До первого category-commit должно быть известно **ожидаемое число импортируемых
категорий**. Эта цифра используется в финальном аудите. Нельзя считать импорт
завершённым только потому, что закончились очевидные листы.

## 2. Определить турнир и архитектуру хранения

Проверить `data/*.json` по названию, датам и городу. Совпали — использовать существующий
slug. Новый `data/<slug>.json` создаётся только для нового соревнования.

Для нового турнира основной файл хранит метаданные соревнования и при необходимости
небольшое число уже существующих категорий, но **новый массовый импорт с самого начала
предпочтительно вести category-fragments**:

```text
data/<slug>.json
data/categories/<slug>/long-cycle-m-63.json
data/categories/<slug>/snatch-f-58.json
data/categories/<slug>/biathlon-m-63.json
```

Одна категория = один fragment-файл. Это уменьшает риск повредить уже внесённые данные
и делает category-commit маленьким и проверяемым.

Перед первым импортом проверить, что `gen_seed.py`, `gen_people.py`, snapshot и другие
потребители действительно подхватывают fragments. Не начинать массовый импорт, пока
эта цепочка не работает.

Для нового турнира выбрать свободный `source.id_base`, не пересекающийся с другими
протоколами, и сразу проверить подключение к:

- `package.json`: `seed:gen`, `db:local`, `db:seed`;
- `.github/workflows/pages.yml`;
- другим сборочным скриптам, если список seed там перечислен вручную.

Новый JSON, который не участвует в локальной БД и workflow, считается незавершённым
импортом.

## 3. Явно описать точность идентификации спортсменов

До первой категории определить, какие поля реально есть в источнике.

Если в источнике нет отчества или полной даты рождения, это должно быть явно отражено
в метаданных источника, например:

```json
{
  "names_without_middle": true,
  "birth_precision": "year"
}
```

Если `names_without_middle: true`, сопоставление с уже известным спортсменом допускается
по **фамилия + имя + год рождения**, даже если в других протоколах у него есть отчество.
Полное каноническое ФИО из более богатого источника не затирать двухсловным именем.
`raw_name` результата сохранять как в текущем протоколе.

Если по `фамилия + имя + год` найдено несколько разных кандидатов — **не объединять
автоматически**. Зафиксировать конфликт и остановить склейку для этой строки до
однозначного решения.

Если источник содержит полную дату рождения, не ослаблять идентификацию без причины.

## 4. Извлечение зависит от формата

### PDF

Если PDF текстовый — извлекать текст/таблицы напрямую. Если скан — использовать
`scripts/ocr_pdf.py` или чтение изображения страницы. Номер страницы сохранять в
`page`; если определить его нельзя — `null`, не угадывать.

Проверять поворот страниц и типичные OCR-подмены: `62,800 → 6240`, `112 → 142`,
запятые/точки в весе, `0/O`, `1/I`.

### Excel

Сначала перечислить листы и понять структуру книги. Не считать автоматически, что
один лист = одна категория: на листе могут быть несколько таблиц, шапок или служебных
блоков.

При чтении Excel:

- учитывать merged cells: значение объединённой шапки относится ко всему диапазону;
- не переносить значение пустой ячейки сверху вниз, если это не очевидная часть оформления;
- различать пустую ячейку, `0` и прочерк;
- даты читать как даты, а не как serial number Excel;
- сохранять десятичный вес без потери дробной части;
- строку считать участником только когда по структуре таблицы это действительно строка результата;
- командные итоги, подписи, рекорды и служебные строки не превращать в спортсменов;
- inventory всех категорий книги завершить до массовой записи.

Если колонка командных очков есть, она может использоваться как сигнал структуры
таблицы, но по указанию администратора её значение не переносить в архив.

### Изображение / скриншот

Читать страницу дважды независимо. Второй проход делается с нуля, до сверки с первым.
Сравнить минимум: **место, результат, собственный вес, год рождения, тренер(ы)**.
При расхождении посмотреть третий раз; не выбирать более «правдоподобное» значение.

## 5. Определить категорию и модель результата

Шапка протокола задаёт параметры категории:

| В источнике | JSON |
| :- | :- |
| Толчок | `discipline: "jerk"` |
| Рывок | `discipline: "snatch"` |
| Толчок по длинному циклу | `discipline: "long_cycle"` |
| Двоеборье | `discipline: "biathlon"` |
| Вес гирь | `bell_kg` |
| Регламент времени | `time_limit_min` |
| Одной/двумя руками | `hands` |
| Весовая категория | `weight_class` |

`weight_class` хранится без `кг`: `"63"`, `"95+"`.

Перед первой категорией каждой новой дисциплины проверить, как она представлена в
схеме БД и генераторе. Нельзя подгонять данные под неподходящее поле.

Стандартные правила результата:

- `jerk`, `snatch`, `long_cycle` — основной результат хранится как количество повторений;
- `biathlon` — итоговые очки хранятся как `points`, а **толчок и рывок отдельно** как
  два значения `result_reps`; итоговые очки нельзя подставлять в `reps` как будто это
  количество подъёмов;
- если встречена новая система подсчёта — сначала проверить/расширить схему и генератор,
  затем импортировать первую категорию.

Неподдерживаемую дисциплину нельзя притворять похожей поддерживаемой. Не вносить её в
результаты; записать в `ERRATA.md` / «Чего в архиве нет» и при необходимости использовать
skill `schema-change`.

## 6. Строки категории

Базовый порядок полей определяется `columns`:

```text
["place", "name", "born", "rank", "region", "club",
 "body_weight_kg", "reps", "rank_achieved", "team_points", "coach"]
```

`region`, `club`, `name`, `born`, `coach` сохраняются максимально близко к источнику.
Прочерк не превращать в выдуманное значение. `born` сохранять с той точностью, которая
есть в протоколе.

Если администратор сказал игнорировать командные очки, ставить значение, совместимое
с текущим генератором (обычно `null`), и не переносить очки как спортивный результат.
Не менять схему ради командных очков.

Эстафеты, командный зачёт и другие секции обрабатываются согласно явной инструкции:

- «игнорируй» → не добавлять в `categories` и не добавлять в `deferred`;
- «добавь позже» → можно завести в `deferred` без выдуманных строк;
- если указания нет — сохранить факт пропуска в `source.note` и `ERRATA.md`, а не
  изобретать данные.

## 7. DNS / DNF / DSQ / снят врачом и другие статусы

Строка участника без числового результата не должна исчезать и не должна получать
выдуманное значение.

Если в источнике написано, например:

- `DNS` / не стартовал;
- `DNF` / не закончил;
- `DSQ` / дисквалифицирован;
- `снят врачом`;

сохранить факт участия/статус в форме, поддерживаемой текущей схемой. Если отдельного
поля статуса пока нет — сохранить строку без выдуманного места/результата и проверить,
как это уже делается в проекте. **Никогда не превращать такой статус в `0` повторений
или придуманное место**, если этого нет в протоколе.

Если схема не позволяет сохранить статус без потери смысла, сначала сделать schema-change.

## 8. Тренеры и персоны

`coach` в JSON — сырой текст протокола. Несколько тренеров должны стать отдельными
связями, но исходная строка сохраняется как напечатана.

После `gen_people.py` проверить:

- тренер вошёл в общую модель `persons`, а не в параллельный справочник;
- человек, уже существующий как спортсмен/деятель/судья, не продублирован без причины;
- несколько тренеров одной строки стали несколькими связями;
- `last_seen_year` означает максимальный год **оцифрованного протокола**, где этот тренер указан у спортсмена;
- старый протокол не уменьшает `last_seen_year`;
- отсутствие тренера в более новом протоколе не удаляет прежнюю связь.

Не сливать тренеров только по похожей фамилии/инициалам. Если тренеры напечатаны без
понятного разделителя (`Иванов И.И. Петров П.П.`), сохранить raw-строку и записать
неоднозначность в `ERRATA.md`; не угадывать разделение.

## 9. Проверить ошибки исходника

Перед коммитом каждой категории искать как минимум:

- результат растёт при ухудшении места;
- собственный вес превышает закрытую весовую категорию;
- спортсмен повторяется внутри категории;
- ФИО совпадает, а год рождения расходится с другими протоколами;
- день/месяц рождения расходятся между выступлениями;
- подозрительные опечатки в ФИО, клубе или тренере;
- строка сдвинута относительно соседних колонок;
- результат противоречит примечанию/рекорду в том же источнике;
- для двоеборья итоговые очки не согласуются с компонентами по правилам протокола.

**Любая подтверждённая проблема записывается в `ERRATA.md` в том же атомарном коммите,
где добавлена соответствующая категория.** Не откладывать ERRATA до конца турнира.

Подтверждённую ошибку составителя протокола сохранять как напечатано. Ошибку нашего
извлечения исправлять в JSON.

## 10. Одна категория = один законченный атомарный цикл

Если администратор просит коммит на каждую категорию, работать строго последовательно:

1. Взять следующую `IMPORT`-категорию из manifest.
2. Извлечь и сверить её полностью.
3. Подготовить её fragment JSON локально/в памяти.
4. Подготовить относящиеся к ней изменения `ERRATA.md`.
5. Перегенерировать/проверить seed и БД.
6. Проверить страницы турнира/спортсмена/персоны.
7. **Только после всех проверок** создать один атомарный Git commit со всеми файлами категории.
8. Push/обновить branch ref один раз.
9. Проверить workflow/deploy.
10. Пометить категорию в progress manifest как `DONE` и только затем переходить к следующей.

Запрещено создавать remote-placeholder, временный файл, commit `x`, частичный JSON или
отдельный «потом допишу ERRATA» commit ради продолжения работы. Если категория меняет
несколько файлов, использовать Git tree/commit так, чтобы они попали в **один commit**.

Если техническая ошибка всё же попала в ветку, сначала полностью восстановить валидное
состояние и убедиться в зелёном deploy, затем продолжать импорт.

## 11. Генерация и проверки

Минимум:

```sh
python3 -c "import json; json.load(open('data/<slug>.json')); print('JSON валиден')"
npm run seed:gen
npm run db:local
npm run snapshot
```

Для fragment-файла также отдельно проверить валидность его JSON.

После появления нового турнира убедиться, что команды действительно генерируют и
подключают **его** данные, включая `data/categories/<slug>/*.json`.

Проверить БД запросами на:

- порядок мест/результатов;
- вес вне категории;
- дубль спортсмена в категории;
- несоответствие `result_reps` итогу;
- рассинхрон параметров результата и категории;
- дубли спортсменов по допустимому ключу идентификации;
- `PRAGMA foreign_key_check`;
- корректность связей persons/coaches и `last_seen_year`.

Непустой результат — сначала расследовать. Не отключать проверку ради зелёной сборки.

## 12. Progress manifest и статус импорта

Во время массового импорта поддерживать рабочий список категорий и обновлять его после
каждого успешного deploy:

```text
ДЦ М 63   DONE <commit>
ДЦ М 68   DONE <commit>
ДЦ М 73   IN_PROGRESS
ДЦ М 78   PENDING
Эстафета  IGNORE
```

На вопрос пользователя «какой статус?» отвечать из этого manifest плюс проверка
текущего состояния репозитория, а не по памяти.

Manifest может быть рабочим/временным и не обязан коммититься, если пользователь не
просил отдельный файл статуса.

## 13. Визуальная проверка

Собранный HTML без ошибок ещё не доказывает правильность данных. Проверить:

- страницу турнира: категория появилась один раз и с верными параметрами;
- таблицу категории: строки и колонки не сдвинуты;
- спортсмена с несколькими дисциплинами: несравнимые серии не соединены одной линией;
- страницу спортсмена: тренеры разделены и годы отображаются корректно;
- страницу персоны: роли спортсмена/тренера/судьи/деятеля находятся на одной странице
  и появляются только при наличии данных.

## 14. Финальный аудит обязателен

После последней категории не завершать задачу сразу. Сначала сверить весь импорт.

Обязательный checklist:

1. Число `IMPORT` в исходном inventory = числу реально импортированных категорий.
2. Каждая ожидаемая комбинация `discipline + sex + weight_class` присутствует ровно один раз.
3. Все category-fragments присутствуют и читаются генераторами.
4. Для каждой категории есть её category-commit либо документированное исправление истории.
5. `IGNORE`-секции действительно отсутствуют в спортивных результатах.
6. Если командные очки велено игнорировать — проверить, что они нигде не импортированы.
7. Нет случайных placeholder/служебных данных в текущем состоянии ветки.
8. `ERRATA.md` содержит все обнаруженные неоднозначности/ошибки источника.
9. `PRAGMA foreign_key_check` чистый.
10. Проверки персон/тренеров проходят, включая правила неполных ФИО.
11. Последний HEAD содержит все category-commits как предков.
12. GitHub Actions/Pages для текущего HEAD завершён успешно.

Итог пользователю сообщать только после этой сверки: сколько категорий ожидалось,
сколько импортировано, что намеренно пропущено и есть ли технические оговорки истории.

## 15. Коммит и деплой

В commit message указать турнир и категорию. Для нового fragment-подхода category-commit
обычно включает сам `data/categories/<slug>/<category>.json` и, если нужно,
`ERRATA.md`; generated seed может создаваться сборкой, если так устроен проект.

Если проект по-прежнему хранит generated seed в репозитории, он должен обновляться в
том же атомарном category-commit — руками seed не править.

Для первой категории нового турнира в тот же атомарный commit могут входить необходимые
правки `package.json`/workflow/generator, чтобы данные реально участвовали в сборке.

После push проверить GitHub Actions. Если workflow упал, это текущая незавершённая
категория: исправить её и добиться зелёного deploy до перехода к следующей.

`verified_by` нельзя выставлять молча: модельное извлечение и автопроверки не равны
человеческой верификации.

## 16. Параллельная работа нескольких агентов

Если есть вероятность, что другой агент или человек одновременно вносит данные в тот же
репозиторий, нельзя считать ранее прочитанный HEAD, manifest или список fragment-файлов
актуальными до конца своей операции.

Правила конкурентной работы:

1. **Перед выбором каждой категории** заново прочитать актуальный HEAD ветки, из которой
   выполняется deploy, и содержимое `data/categories/<slug>/`. Категорию брать в работу
   только если её fragment ещё отсутствует и по истории не видно, что другой агент уже
   заканчивает тот же импорт.
2. **Непосредственно перед записью/коммитом** ещё раз проверить HEAD и целевой fragment.
   Если fragment уже появился, не перезаписывать его и не создавать второй category-commit.
   Сначала сверить существующий файл с источником. Если он корректен — считать категорию
   уже выполненной другим агентом; если есть расхождение — остановить автоматическое
   внесение этой категории и расследовать конфликт.
3. **Force push, reset и переписывание чужой истории запрещены.** Если branch ref сдвинулся
   и обновление не является fast-forward, перечитать новый HEAD и повторить только своё
   изменение поверх него. Чужие commits должны остаться предками нового HEAD.
4. По возможности агенты должны брать **непересекающиеся категории**. Общие файлы вроде
   `ERRATA.md` перед атомарным category-commit перечитывать заново и объединять своё
   дополнение с актуальной версией, не затирая записи другого агента.
5. Если администратор требует «каждую категорию мержить в default-ветку, чтобы триггерился
   deploy», определить фактическую default/deploy-ветку из репозитория и workflow и
   интегрировать туда каждую категорию отдельно. Commit только в рабочей ветке не считается
   завершением категории.
6. Успешность deploy проверять по `head_sha`. Категория считается задеплоенной, если
   либо workflow для её собственного commit завершился `success`, либо более поздний
   успешный deploy выполнен для HEAD, который содержит category-commit как предка.
   Это важно при concurrency/cancel-in-progress: отменённый run не означает потерю
   категории, если следующий зелёный deploy уже включает её commit.
7. После каждого успешного deploy заново синхронизировать progress manifest с текущим
   состоянием репозитория: за время проверки другой агент мог добавить несколько
   категорий. Уже появившиеся категории не импортировать повторно.
8. Атомарный цикл раздела 10 остаётся обязательным **для каждой категории каждого
   агента**: не начинать следующую свою категорию, пока текущая не интегрирована и не
   подтверждена успешным deploy согласно правилу выше.
9. Финальный аудит выполнять по актуальному HEAD deploy-ветки, а не по локальному или
   ранее прочитанному состоянию. Дополнительно проверить отсутствие двух fragments для
   одной комбинации `discipline + sex + weight_class` и убедиться, что все category-commits
   всех агентов являются предками финального HEAD.

Если два агента случайно выбрали одну категорию, приоритет имеет уже интегрированный
валидный fragment. Второй агент не должен «побеждать» перезаписью: он либо подтверждает
существующие данные и переключается на следующую категорию, либо фиксирует реальный
конфликт для ручного разбора.
