# Импорт протокола

Источник может быть **PDF, Excel или изображение**. Формат меняет только этап извлечения;
после получения строк категории правила одинаковые.

## Главный принцип

**Источник является авторитетом для импортируемых значений.**

Задача импорта — не проверять, правильно ли составлен протокол, а точно перенести то,
что в нём написано. Странные, нелогичные или противоречивые значения не исправлять и
не расследовать во время обычного импорта.

Примеры того, что сохраняется как есть:

- результат у второго места выше, чем у первого;
- собственный вес выше указанной весовой категории;
- год или дата рождения отличаются от другого протокола;
- ФИО, клуб или тренер выглядят как опечатка;
- итог двоеборья выглядит необычно или не сходится с ожидаемой формулой;
- одно и то же имя встречается в категории несколько раз.

Проверять нужно только **точность переноса**: правильная ли строка, колонка, число,
категория и страница были прочитаны из источника. Ошибка извлечения исправляется в JSON.
Ошибка или странность самого источника остаётся как напечатано.

`ERRATA.md` не является обязательной частью обычного импорта. Добавлять запись туда
только если администратор отдельно просит анализировать или документировать ошибки
исходного протокола.

Явные инструкции администратора важнее дефолтов skill. Например, если сказано
«эстафеты и командные очки игнорируй», их не добавлять даже в `deferred`.

## 1. Inventory источника

Перед массовой записью один раз определить, какие индивидуальные категории есть в
источнике и какие из них нужно импортировать.

Для Excel — просмотреть листы и таблицы. Для PDF — страницы/разделы. Для набора
изображений — все изображения/страницы.

Рабочий список может быть простым:

```text
ДЦ М 63   IMPORT
ДЦ М 68   IMPORT
Р Ж 58    IMPORT
Эстафета  IGNORE
Жонглирование UNSUPPORTED
```

Статусы:

- `IMPORT` — индивидуальная категория, которую нужно внести;
- `IGNORE` — не импортировать;
- `UNSUPPORTED` — текущая схема не представляет данные корректно;
- `DEFERRED` — только если администратор явно просит отложить.

Inventory нужен только для полноты импорта. Не превращать его в отдельный аудит
качества протокола.

## 2. Турнир и хранение

Проверить существующие `data/*.json` по названию, датам и городу. Если турнир уже есть —
использовать существующий slug. Новый `data/<slug>.json` создавать только для нового
соревнования.

Для массового импорта предпочтительны category-fragments:

```text
data/<slug>.json
data/categories/<slug>/long-cycle-m-63.json
data/categories/<slug>/snatch-f-58.json
data/categories/<slug>/biathlon-m-63.json
```

Одна категория = один fragment-файл.

Для нового турнира выбрать свободный `source.id_base` и убедиться, что данные подключены
к генератору/локальной БД/workflow. Эта проверка делается для турнира, а не заново для
каждой категории.

## 3. Идентификация спортсменов

Сохранять точность имени и даты рождения такой, какая есть в источнике.

Если нет отчества или полной даты рождения, это можно указать в метаданных:

```json
{
  "names_without_middle": true,
  "birth_precision": "year"
}
```

Если `names_without_middle: true`, сопоставление допускается по фамилии + имени + году
рождения. Более полное каноническое ФИО не затирать более бедным источником.
`raw_name` результата всегда сохранять из текущего протокола.

Если найдено несколько возможных людей — не угадывать и не сливать автоматически.
Это техническая неоднозначность идентификации, а не повод останавливать перенос самой
строки протокола.

## 4. Извлечение по формату

### PDF

Если PDF текстовый — извлекать текст/таблицы напрямую. Если скан — использовать
`scripts/ocr_pdf.py` или чтение изображения страницы. Номер страницы сохранять в
`page`; если определить нельзя — `null`.

Для OCR обязательно защищаться от **наших ошибок распознавания**: поворот страницы,
`62,800 → 6240`, `112 → 142`, запятые/точки, `0/O`, `1/I`.

Это проверка переноса, а не проверка правдоподобия результата.

### Excel

Учитывать структуру таблицы:

- merged cells;
- пустая ячейка, `0` и прочерк — разные значения;
- даты читать как даты;
- десятичный вес сохранять без потери дробной части;
- не превращать подписи, итоги и служебные строки в спортсменов.

Не проверять спортивную правдоподобность значений из Excel.

### Изображение / скриншот

Если текст/цифры плохо читаются, повторно посмотреть спорное место, чтобы убедиться,
что значение прочитано правильно. Не делать обязательный независимый второй проход
всей страницы, если она читается однозначно.

При сомнении между двумя значениями сверять изображение, а не выбирать более
«правдоподобное» спортивно.

## 5. Категория и модель результата

Шапка протокола задаёт параметры категории:

| В источнике | JSON |
| :- | :- |
| Толчок | `discipline: "jerk"` |
| Рывок | `discipline: "snatch"` |
| Толчок по длинному циклу | `discipline: "long_cycle"` |
| Двоеборье | `discipline: "biathlon"` |
| Вес гирь | `bell_kg` |
| Регламент времени | `time_limit_min` |
| Одной/двумя руками | `hands` |
| Весовая категория | `weight_class` |

`weight_class` хранится без `кг`: `"63"`, `"95+"`.

Стандартные правила хранения:

- `jerk`, `snatch`, `long_cycle` — основной результат как количество повторений;
- `biathlon` — итоговые очки как `points`, толчок и рывок отдельно как `result_reps`;
- неизвестную систему подсчёта не подгонять под неподходящее поле.

Если схема не умеет представить данные без потери смысла — это техническая проблема
схемы. Использовать `schema-change` или оставить раздел `UNSUPPORTED`.

## 6. Строки категории

Базовый порядок полей определяется `columns`:

```text
["place", "name", "born", "rank", "region", "club",
 "body_weight_kg", "reps", "rank_achieved", "team_points", "coach"]
```

`region`, `club`, `name`, `born`, `coach` сохраняются максимально близко к источнику.
Прочерк не превращать в выдуманное значение. `born` сохранять с той точностью, которая
есть в протоколе.

Если командные очки велено игнорировать — не переносить их как спортивный результат.

Эстафеты, командный зачёт и другие секции обрабатывать по явной инструкции
администратора. Если раздел не поддерживается, не изобретать представление данных.

## 7. DNS / DNF / DSQ и другие статусы

Строка участника без числового результата не должна исчезать и не должна получать
выдуманное значение.

Если в источнике указано `DNS`, `DNF`, `DSQ`, `снят врачом` и т.п., сохранить статус в
форме, которую поддерживает схема. Не превращать статус в `0` повторений или придуманное
место, если этого нет в протоколе.

Если схема не позволяет сохранить статус без потери смысла — использовать schema-change.

## 8. Тренеры и персоны

`coach` в JSON — сырой текст протокола. Исходную строку сохранять как напечатана.

`gen_people.py` может строить производные связи. Во время обычного импорта не требуется
ручной аудит всех персон, ролей, дублей и `last_seen_year` после каждой категории.

Не сливать людей только по похожей фамилии/инициалам. Если строка тренеров неоднозначна,
сохранить raw-текст и не угадывать разделение.

## 9. Что НЕ проверять при обычном импорте

Не тратить время на поиск и расследование ошибок составителя протокола. В частности,
не являются блокирующими проверками:

- порядок мест относительно величины результата;
- собственный вес относительно весовой категории;
- повтор спортсмена внутри категории;
- расхождения ФИО или даты рождения с другими протоколами;
- подозрительные опечатки в ФИО, клубе или тренере;
- спортивная правдоподобность результата;
- соответствие примечаниям или рекордам;
- пересчёт или проверка формулы итоговых очков двоеборья.

Если такое значение действительно стоит в источнике — **импортировать его как есть**.

Единственное исключение: если странность указывает на возможный сдвиг колонок,
неверное чтение OCR или другую ошибку нашего переноса, сверить конкретную строку с
источником.

## 10. Цикл импорта категории

Для каждой `IMPORT`-категории:

1. Прочитать шапку и строки.
2. Сверить только неоднозначные места чтения.
3. Создать fragment JSON.
4. Проверить валидность JSON.
5. Убедиться, что целевого fragment ещё нет или что он не добавлен другим агентом.
6. Commit/merge согласно текущей задаче пользователя.
7. Перейти к следующей категории.

Не требуется перед каждой следующей категорией:

- расследовать качество исходного протокола;
- обновлять `ERRATA.md`;
- вручную проверять страницы спортсмена/персоны;
- ждать завершения deploy, если пользователь отдельно этого не требует.

## 11. Минимальные технические проверки

Обязательные проверки должны защищать только от поломки импорта:

```sh
python3 -c "import json; json.load(open('data/<slug>.json')); print('JSON валиден')"
npm run seed:gen
```

Для fragment-файла отдельно проверить валидность JSON.

После пачки категорий или перед завершением импорта запустить:

```sh
npm run db:local
```

и проверить:

```sql
PRAGMA foreign_key_check;
```

Если менялась схема, генератор или UI — дополнительно выполнить соответствующие
проверки (`snapshot`, визуальная проверка и т.п.). Для простого добавления данных они
не обязательны после каждой категории.

Не делать блокирующими SQL-проверками спортивную логику значений из протокола.

## 12. Progress/status

Во время массового импорта можно вести простой рабочий список:

```text
ДЦ М 63   DONE
ДЦ М 68   DONE
ДЦ М 73   IN_PROGRESS
ДЦ М 78   PENDING
Эстафета  IGNORE
```

На вопрос пользователя о статусе сверять этот список с актуальным состоянием
репозитория.

## 13. Финальная проверка

После последней категории нужна короткая проверка полноты и технической целостности:

1. Все ожидаемые `IMPORT`-категории получили данные.
2. Нет случайно потерянных или дважды созданных fragment-файлов одной категории.
3. Генератор читает новые fragments.
4. Локальная БД собирается.
5. `PRAGMA foreign_key_check` чистый.
6. `IGNORE`-разделы не были импортированы по ошибке.

Не проводить финальный аудит спортивной достоверности протокола, если пользователь
отдельно этого не просит.

## 14. Коммит и деплой

В commit message указывать турнир и категорию, если импорт идёт по категориям.
Generated seed руками не править.

Если пользователь требует отдельный merge/deploy для каждой категории — выполнить это.
В остальных случаях не ждать GitHub Actions после каждой категории: можно продолжать
следующую категорию и проверить итоговый deploy после завершения пачки.

`verified_by` нельзя выставлять молча: модельное извлечение не является человеческой
верификацией.

## 15. Параллельная работа нескольких агентов

Если другой агент или человек может работать одновременно:

1. Перед выбором категории проверить актуальный HEAD и наличие целевого fragment.
2. Непосредственно перед записью ещё раз проверить, что fragment не появился.
3. Уже существующий валидный fragment не перезаписывать.
4. Force push, reset и переписывание чужой истории запрещены.
5. Общие файлы перечитывать перед записью, чтобы не затереть чужие изменения.
6. По возможности брать непересекающиеся категории.
7. После завершения сверить итог по актуальному HEAD deploy-ветки.

Если два агента выбрали одну категорию, приоритет у уже интегрированного валидного
fragment. Второй агент либо подтверждает его и переключается дальше, либо разбирает
реальное расхождение данных с источником.
