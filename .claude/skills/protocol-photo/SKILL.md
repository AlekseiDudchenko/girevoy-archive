# Импорт протокола

Источник может быть **PDF, Excel или изображение**. Формат меняет только этап извлечения;
после получения строк категории правила одинаковые.

Данные настоящие. Не исправлять их догадкой и не «нормализовать» исходник молча.
Странное, но подтверждённое значение сохраняется как в протоколе и фиксируется в
`ERRATA.md`. Ошибка извлечения исправляется в JSON, а факт ошибки можно записать в
раздел «Исправленное».

Явные инструкции администратора важнее дефолтов skill. Например, если сказано
«эстафеты и командные очки игнорируй», их не добавлять даже в `deferred`.

## 1. Сначала определить турнир

До извлечения проверить `data/*.json` по названию, датам и городу. Совпали — новая
категория дописывается в существующий файл. Новый `data/<slug>.json` создаётся только
для нового соревнования.

Проверить `source.note`: какие разделы уже внесены, что сознательно пропущено, известны
ли страницы. Нельзя заводить второй slug тому же турниру.

Для нового турнира выбрать свободный `source.id_base`, не пересекающийся с другими
протоколами, и сразу проверить, как новый seed должен подключаться к:

- `package.json`: `seed:gen`, `db:local`, `db:seed`;
- `.github/workflows/pages.yml`;
- другим сборочным скриптам, если список seed там перечислен вручную.

Новый JSON/SQL, который не участвует в локальной БД и workflow, считается незавершённым
импортом.

## 2. Извлечение зависит от формата

### PDF

Если PDF текстовый — извлекать текст/таблицы напрямую. Если скан — использовать
`scripts/ocr_pdf.py` или чтение изображения страницы. Номер страницы сохранять в
`page`; если определить его нельзя — `null`, не угадывать.

Проверять поворот страниц и типичные OCR-подмены: `62,800 → 6240`, `112 → 142`,
запятые/точки в весе, `0/O`, `1/I`.

### Excel

Сначала перечислить листы и понять структуру книги. Не считать автоматически, что
один лист = одна категория: на листе могут быть несколько таблиц, шапок или служебных
блоков.

При чтении Excel:

- учитывать merged cells: значение объединённой шапки относится ко всему диапазону;
- не переносить значение пустой ячейки сверху вниз, если это не очевидная часть
  оформления;
- различать пустую ячейку, `0` и прочерк;
- даты читать как даты, а не как serial number Excel;
- сохранять десятичный вес без потери дробной части;
- строку считать участником только когда по структуре таблицы это действительно строка
  результата, а не заголовок/итог/командный зачёт;
- найти все категории книги до начала массовой записи и составить их перечень.

Если колонка командных очков есть, она может использоваться как сигнал сдвига строки,
но по указанию администратора её значение допускается не переносить в архив.

### Изображение / скриншот

Читать страницу дважды независимо. Второй проход делается с нуля, до сверки с первым.
Сравнить минимум: **место, результат, собственный вес, год рождения, тренер(ы)**.
При расхождении посмотреть третий раз; не выбирать более «правдоподобное» значение.

## 3. Определить категорию

Шапка протокола задаёт параметры категории:

| В источнике | JSON |
| :- | :- |
| Толчок | `discipline: "jerk"` |
| Рывок | `discipline: "snatch"` |
| Толчок по длинному циклу | `discipline: "long_cycle"` |
| Двоеборье | `discipline: "biathlon"` |
| Вес гирь | `bell_kg` |
| Регламент времени | `time_limit_min` |
| Одной/двумя руками | `hands` |
| Весовая категория | `weight_class` |

`weight_class` хранится без `кг`: `"63"`, `"95+"`.

Неподдерживаемую дисциплину нельзя притворять похожей поддерживаемой. Не вносить её в
результаты; записать в `ERRATA.md` / «Чего в архиве нет» и при необходимости использовать
skill `schema-change`.

## 4. Строки категории

Порядок полей определяется `columns`:

```text
["place", "name", "born", "rank", "region", "club",
 "body_weight_kg", "reps", "rank_achieved", "team_points", "coach"]
```

`region`, `club`, `name`, `born`, `coach` сохраняются максимально близко к источнику.
Прочерк не превращать в выдуманное значение. `born` сохранять полностью, даже если
склейка спортсмена использует только год.

Если администратор сказал игнорировать командные очки, ставить значение, совместимое
с текущим генератором (обычно `null`), и не переносить очки как спортивный результат.
Не менять схему ради командных очков.

Эстафеты, командный зачёт и другие секции обрабатываются согласно явной инструкции:

- «игнорируй» → не добавлять в `categories` и не добавлять в `deferred`;
- «добавь позже» → можно завести в `deferred` без выдуманных строк;
- если указания нет — сохранить факт пропуска в `source.note` и `ERRATA.md`, а не
  изобретать данные.

## 5. Тренеры и персоны

`coach` в JSON — сырой текст протокола. Несколько тренеров должны стать отдельными
связями, но исходная строка сохраняется как напечатана.

После `gen_people.py` проверить:

- тренер вошёл в общую модель `persons`, а не в параллельный справочник;
- человек, уже существующий как спортсмен/деятель/судья, не продублирован без причины;
- несколько тренеров одной строки стали несколькими связями;
- `last_seen_year` означает максимальный год **оцифрованного протокола**, где этот
  тренер указан у спортсмена;
- старый протокол не уменьшает `last_seen_year`;
- отсутствие тренера в более новом протоколе не удаляет прежнюю связь.

Не сливать тренеров только по похожей фамилии/инициалам. Неоднозначность фиксировать,
а не угадывать.

## 6. Проверить ошибки исходника

Перед коммитом каждой категории искать как минимум:

- результат растёт при ухудшении места;
- собственный вес превышает закрытую весовую категорию;
- спортсмен повторяется внутри категории;
- ФИО совпадает, а год рождения расходится с другими протоколами;
- день/месяц рождения расходятся между выступлениями;
- подозрительные опечатки в ФИО, клубе или тренере;
- строка сдвинута относительно соседних колонок;
- результат противоречит примечанию/рекорду в том же источнике.

**Любая подтверждённая проблема записывается в `ERRATA.md` в том же коммите, где
добавлена соответствующая категория.** Не откладывать ERRATA до конца всего турнира.

Подтверждённую ошибку составителя протокола сохранять как напечатано. Ошибку нашего
извлечения исправлять в JSON.

## 7. Одна категория = один законченный цикл

Если администратор просит коммит на каждую категорию, работать строго последовательно:

1. Извлечь одну категорию.
2. Добавить только её в `data/<slug>.json`.
3. Обновить `source.note`, если изменился охват.
4. Перегенерировать соответствующий `seeds/*.sql`; seed руками не править.
5. Добавить найденные проблемы в `ERRATA.md`.
6. Собрать локальную БД и выполнить проверки.
7. Проверить страницы турнира/спортсмена/персоны.
8. Сделать отдельный commit этой категории.
9. Push в ветку, на которую настроен Pages/deploy.
10. Проверить workflow/deploy; только после успешной сборки переходить к следующей
    категории.

Не пакетировать несколько категорий в один коммит, если пользователь явно попросил
отдельный коммит на каждую.

## 8. Генерация и проверки

Минимум:

```sh
python3 -c "import json; json.load(open('data/<slug>.json')); print('JSON валиден')"
npm run seed:gen
npm run db:local
npm run snapshot
```

После появления нового турнира убедиться, что команды действительно генерируют и
подключают **его** seed, а не только старые файлы.

Проверить БД запросами на:

- порядок мест/результатов;
- вес вне категории;
- дубль спортсмена в категории;
- несоответствие `result_reps` итогу;
- рассинхрон параметров результата и категории;
- дубли спортсменов по ФИО+году;
- `PRAGMA foreign_key_check`;
- корректность связей persons/coaches и `last_seen_year`.

Непустой результат — сначала расследовать. Не отключать проверку ради зелёной сборки.

## 9. Визуальная проверка

Собранный HTML без ошибок ещё не доказывает правильность данных. Проверить:

- страницу турнира: категория появилась один раз и с верными параметрами;
- таблицу категории: строки и колонки не сдвинуты;
- спортсмена с несколькими дисциплинами: несравнимые серии не соединены одной линией;
- страницу спортсмена: тренеры разделены и годы отображаются корректно;
- страницу персоны: роли спортсмена/тренера/судьи/деятеля находятся на одной странице
  и появляются только при наличии данных.

## 10. Коммит и деплой

В commit message указать турнир и категорию. В изменениях категории должны вместе идти
`data/<slug>.json`, сгенерированный seed и относящиеся к категории записи `ERRATA.md`.
Для первой категории нового турнира в этот же коммит могут входить необходимые правки
`package.json`/workflow, чтобы новый seed реально участвовал в сборке.

После push проверить GitHub Actions. Если workflow упал, это текущая незавершённая
категория: исправить её и деплой до перехода к следующей.

`verified_by` нельзя выставлять молча: модельное извлечение и автопроверки не равны
человеческой верификации.
