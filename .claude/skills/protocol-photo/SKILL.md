# Протокол с фотографии

Для PDF есть `scripts/ocr_pdf.py`. Здесь другой случай: страница уже пришла картинкой,
распознавать нечем и незачем — её читает модель, то есть вы. Это снимает OCR-ошибки
вида `62,800 → 6240`, но не снимает главный риск проекта: «112» вместо «142» выглядит
правдоподобно и молча уходит в базу.

Данные настоящие. Не достраивать пропуски догадкой, не выравнивать странное под
ожидаемое: колонка с прочерками остаётся прочерками, спортсмен, записанный дважды, —
находка автопроверки, а не повод одну строку убрать.

## 1. Сначала выяснить, знаком ли турнир

Главная ловушка — завести второй `slug` тому же соревнованию и получить два турнира
вместо одного. До извлечения:

```sh
ls data/                                            # какие турниры уже есть
grep -l "Чемпионат России 2026" data/*.json         # искать по названию, не по slug
python3 -c "import json,glob
for f in glob.glob('data/*.json'):
    d=json.load(open(f))
    c=d['competition']
    print(f, '|', c['slug'], c['date_start'], c['city'], '| категорий:', len(d['categories']))
    print('   ', d['source']['note'][:120])"
```

Совпали название, даты и город — это тот же турнир, и новая категория **дописывается
в его файл**. Отдельный `data/*.json` заводится только под новое соревнование.

Заодно прочитайте `source.note` того файла: там записано, какие разделы уже оцифрованы.
Если ваша страница уже там — работа сделана до вас, сверьте числа и остановитесь.

## 2. Прочитать страницу дважды

Требование FR-A17 — два независимых прогона. С картинкой второй прогон это не второй
запуск скрипта, а повторное чтение изображения с нуля, до сверки с первым результатом.
Механически: выписать все числа, отложить, прочитать заново, сравнить колонки
**результат**, **собственный вес**, **место**, **год рождения** и **тренер(ы)**.

Разошлись — не выбирать «правдоподобное», а смотреть на картинку третий раз. Если
разрешить не удалось, строка идёт в `issues` с `kind='run_mismatch'`, а не в базу.

Дешёвые сигналы, что прочитано верно:

- результаты не возрастают с местом;
- собственный вес у всех укладывается в весовую категорию;
- командные очки убывают шагом 20, 18, 16, 15, 14… — сбой в этом ряду часто значит,
  что строка прочитана со сдвигом;
- рекорд в шапке, если он есть, выше лучшего результата в таблице;
- список тренеров не «переехал» на соседнюю строку спортсмена.

## 3. Разложить шапку по полям

Шапка протокола — это параметры **категории**, а не дисциплины:

| В протоколе | Куда |
| :- | :- |
| «Толчок», «Рывок», «Толчок по длинному циклу» | `discipline`: `jerk`, `snatch`, `long_cycle`, `biathlon` |
| «Вес гирь 32 кг» | `bell_kg` |
| «Регламент времени — 10 мин.» | `time_limit_min` |
| «одной рукой» в заголовке | `hands: "one"`, дисциплина не меняется |
| «Весовая категория 63 кг» | `weight_class: "63"` |
| «+95», «свыше 95» | `weight_class: "95+"` |

`weight_class` пишется **без единицы**: «кг» дописывает рендер, иначе на странице
выходит «63 кг кг».

Дисциплину из регламента и числа рук не собирать: «длинный цикл одной рукой 30 минут» —
это `long_cycle` плюс `hands` плюс `time_limit_min`, а не строка справочника.

## 4. Дописать категорию в `data/<slug>.json`

Порядок полей строки задан `columns` в начале файла:

```
["place", "name", "born", "rank", "region", "club",
 "body_weight_kg", "reps", "rank_achieved", "team_points", "coach"]
```

```json
{
  "page": null, "discipline": "jerk", "sex": "m", "bell_kg": 32, "hands": "two",
  "time_limit_min": 10, "weight_class": "63", "norms": null,
  "note": "Откуда страница и что в ней нестандартного.",
  "rows": [
    [1, "Фамилия Имя Отчество", "04.07.1990", "ЗМС", "г. Санкт-Петербург",
     "СПБ ГБУ ДО СШОРСВС им. В.Ф. Краевского", 62.800, 142, "-", 20, "Кириллов С.А."]
  ]
}
```

Что важно в значениях:

- **`region` и `club` — как в протоколе.** «г. Санкт-Петербург» с приставкой, кавычки
  и номера школ на месте. Генератор кладёт это в `raw_region` и `raw_club`, а регион
  для справочника берёт как `split(",")[0]`.
- **`born` целиком**, хотя в базу идёт только год: день и месяц остаются в JSON
  как след исходника.
- **`rank_achieved`** — графа «Выполненный разряд». Прочерк оставить прочерком,
  `gen_seed.py` превратит его в `NULL`. «+МС» тоже допустимо, разбирается.
- **`page`** — номер страницы в исходном документе. Для картинки из чата он обычно
  неизвестен: тогда `null`, и `results.source_page` останется пустым. Не выдумывать.
- **`norms`** — разрядные нормативы из шапки. Прочерки → `null`. Генератор их
  не читает, это пометка для человека.

Категории с результатами идут в `categories`, неоцифрованное (эстафеты, командный
зачёт) — в `deferred`, оттуда получится `is_deferred = 1` и пометка «будет добавлено
позже». Придумывать строки эстафеты нельзя, завести её отложенной — нужно.

### Тренеры и персоны

`coach` в строке JSON — это **сырой текст протокола**, а не уже нормализованная персона.
Его нужно сохранять максимально близко к источнику: инициалы, порядок фамилии и
инициалов, сокращения и разделители не «улучшать» вручную.

Если у спортсмена указано несколько тренеров, **не склеивать их в одного человека**.
Разделить список на отдельных тренеров по фактическим разделителям протокола
(запятая, точка с запятой, перенос строки и т.п.) так, чтобы каждый тренер получил
отдельную связь со спортсменом. Не делить строку по запятой механически, если запятая
является частью ФИО или оформления источника.

После генерации проверить, что тренеры попали в общую модель персон, а не образовали
параллельный справочник. Одна и та же персона может одновременно иметь несколько
ролей: **спортивный деятель**, **спортсмен**, **тренер**, **судья**. Не создавать
отдельную «персону-тренера», если человек уже существует как спортсмен или деятель.

Для связи «спортсмен — тренер» архив хранит не выдуманный период работы, а факт,
когда тренер **последний раз был указан в доступных протоколах**. При добавлении
нового протокола:

- если связь спортсмена с этим тренером новая — создать её с годом этого турнира;
- если такая связь уже есть — обновить `last_seen_year` только если год нового
  протокола больше сохранённого;
- более старый протокол не должен уменьшать `last_seen_year`;
- если в одном протоколе несколько тренеров, каждый получает собственную связь и
  собственный `last_seen_year`;
- отсутствие тренера в более позднем протоколе **не означает**, что сотрудничество
  прекратилось, и не является основанием удалять старую связь.

`last_seen_year` означает именно «последний год, когда этот тренер указан рядом с
этим спортсменом в оцифрованном протоколе», а не «год окончания тренерской работы».
На странице спортсмена и странице персоны это должно отображаться как справочная
информация, например `Иванов И.И. (2024)`.

При нормализации ФИО тренера нельзя сливать людей только по похожей фамилии или
инициалам. Если идентичность не подтверждается данными проекта, сохранить отдельную
персону/неоднозначность и зафиксировать это в `issues`, а не угадывать.

### Чему в схеме места нет

Не пытаться пристроить, просто знать: **командные очки**, номер ЕКП, число регионов
и участников по турниру целиком, рекорд из шапки, состав судейской коллегии. Если
такое поле понадобится всерьёз — это правка схемы, скилл `schema-change`.

Отдельно: «Количество участников» в шапке — по всему чемпионату, а не по вашей
категории. В `participants_declared` его не класть: `gen_seed.py` проставит туда
число строк, и автопроверка `row_count` останется осмысленной.

### Один и тот же спортсмен в нескольких категориях

Ключ склейки в `gen_seed.py` — фамилия, имя, отчество и **год** рождения. Совпало —
это одна запись с несколькими выступлениями, и так и должно быть.

Отсюда два следствия. Расхождение в дне и месяце (`02.05.2007` против `05.02.2007`)
записи не раздваивает и на базу не влияет, но означает ошибку в одном из исходников —
сказать о ней, а не молча выбрать любую. А вот разный год рождения разведёт одного
человека на двух спортсменов: если фамилия, имя и отчество совпали, а год нет —
перечитать обе страницы, прежде чем генерировать.

## 5. Пересобрать и проверить

`seeds/*.sql` руками не правятся: следующая генерация затрёт правку.

```sh
python3 -c "import json;json.load(open('data/<slug>.json'));print('JSON валиден')"
npm run seed:gen
npm run db:local
npm run snapshot
```

Диффом сида убедиться, что изменение локальное: перетасовка всего файла значит,
что поехал порядок генерации, и это чинится, а не коммитится.

Автопроверки FR-A5 прогнать запросами по собранной базе, а не глазами. Каждый
должен вернуть пусто:

```sh
sqlite3 .local/girevoy.db <<'SQL'
.mode line
-- места не по убыванию результата
SELECT a.id FROM results a JOIN results b
  ON a.category_id = b.category_id AND a.place < b.place AND a.result_value < b.result_value;
-- личный вес вне весовой категории
SELECT r.id, r.body_weight_kg FROM results r JOIN categories c ON c.id = r.category_id
 WHERE c.weight_class_is_open = 0 AND r.body_weight_kg > c.weight_class_kg;
-- спортсмен дважды в одной категории
SELECT category_id, athlete_id, COUNT(*) FROM results GROUP BY 1, 2 HAVING COUNT(*) > 1;
-- подъёмы не сходятся с итогом
SELECT r.id FROM results r JOIN result_reps rr ON rr.result_id = r.id
 WHERE rr.reps <> r.total_reps;
-- продублированный ключ серии разъехался с категорией
SELECT r.id FROM results r JOIN categories c ON c.id = r.category_id
 WHERE r.discipline_id <> c.discipline_id OR r.bell_kg <> c.bell_kg
    OR r.hands <> c.hands OR r.time_limit_min <> c.time_limit_min;
-- дубли спортсменов по ФИО и году
SELECT full_name, birth_year, COUNT(*) FROM athletes GROUP BY last_name, first_name, middle_name, birth_year HAVING COUNT(*) > 1;
PRAGMA foreign_key_check;
SQL
```

Дополнительно проверить модель персон и тренеров запросами, соответствующими текущей
схеме проекта:

- одна персона не продублирована отдельно как спортсмен и тренер;
- у одного спортсмена нет двух одинаковых связей с одним тренером;
- для каждой связи `last_seen_year` совпадает с максимальным годом оцифрованного
  протокола, где этот тренер указан у этого спортсмена;
- несколько тренеров из одной строки протокола превратились в несколько связей.

Если имена таблиц или полей после миграции изменились, сначала посмотреть текущую
схему и адаптировать запросы — не добавлять в skill устаревший SQL только ради
формальной проверки.

Непустой ответ — это либо ошибка извлечения (чаще), либо ошибка составителя протокола
(бывает). Первое чинится в JSON, второе сохраняется как есть и заводится в `issues`.

Если `sqlite3` не поставлен, его ставит `scripts/setup_env.sh`; в крайнем случае
те же файлы разворачиваются через `node:sqlite`.

## 6. Посмотреть страницы

Собранный HTML без ошибок не значит, что всё на месте.

- **Страница турнира** — новая категория появилась в списке-чипсах, условия рядом
  с числами верные, таблица не разъехалась.
- **Карточка спортсмена, выступавшего в двух категориях** — самый показательный
  случай. Разные серии обязаны быть разными линиями и разными цветами: результат
  толчка и результат длинного цикла несравнимы, соединять их линией нельзя.
- **Страница спортсмена** — все тренеры показаны отдельно, рядом указан их
  `last_seen_year`; один тренер не повторяется несколько раз.
- **Страница персоны-тренера** — связь ведёт на ту же персону, а если этот человек
  также спортсмен, судья или спортивный деятель, соответствующие разделы находятся
  на одной странице персоны и появляются только при наличии данных.

## 7. Коммит

В сообщении: турнир и категория, сколько строк, что показали автопроверки, и отдельно —
чего в данных нет и почему (неизвестная страница, потерянные командные очки,
расхождение в дате рождения, неоднозначный тренер). Это единственное место, где такие
оговорки сохраняются.

Коммитить `data/<slug>.json` и сгенерированный `seeds/*.sql` вместе: врозь они
рассинхронизируются, и станет непонятно, какой SQL из какого JSON собран.

Если изменение затрагивает нормализацию персон или связи тренеров, проверить дифф
особенно внимательно: добавление одной страницы протокола не должно массово менять
идентификаторы уже существующих персон.

`gen_seed.py` ставит турниру `is_published = 1`, а `verified_by` оставляет пустым:
строка опубликована моделью и человеком не сверена. Молчаливо выставлять верификацию
нельзя.
