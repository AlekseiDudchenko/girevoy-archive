# Изменение схемы

Схема живёт в `migrations/`, пояснения к неочевидным местам — в `docs/schema.md`,
решения, из которых она следует, — в `docs/decisions.md`. Правка схемы почти всегда
тянет за собой демо-данные и снимок сайта: пропустить эти шаги значит оставить
репозиторий в состоянии, где `npm run preview` падает.

## Сначала проверить, правда ли нужна новая сущность

Частая ошибка в этом проекте — заводить строку справочника под каждое сочетание
условий. Прежде чем добавлять таблицу или значение в справочник, проверьте по
`CLAUDE.md`, не является ли это параметром существующей сущности:

- новый вариант дисциплины («одной рукой», «30 минут», «полумарафон») — это
  `hands` и `time_limit_min` в `categories`, а не строка в `disciplines`;
- новый набор весовых категорий — ничего не требует, они хранятся как в протоколе;
- новый зачёт по уровню — строка в `divisions`.

Если сущность всё-таки нужна, продолжайте.

## Куда писать миграцию

Пока схема не применена ни на одной живой базе (`wrangler d1 execute` не запускался
на боевой), правьте `0001_init.sql` на месте — это честнее, чем цепочка миграций,
из которых половина отменяет предыдущую.

Как только база развёрнута, только новый файл: `migrations/0002_<что_меняется>.sql`.
SQLite не умеет менять и удалять колонки произвольно, поэтому перенос данных пишется
через создание новой таблицы, `INSERT ... SELECT` и переименование.

## Проверка

Выполнять целиком, не выборочно. Первые две проверки ловят почти всё.

```sh
# 1. Схема выполняется на чистой базе
python3 - <<'PY'
import sqlite3
c = sqlite3.connect(':memory:')
for f in ('migrations/0001_init.sql',):   # + новые миграции по порядку
    c.executescript(open(f, encoding='utf-8').read())
print('схема ок')
PY

# 2. Схема принимает связанные записи и не рвёт ссылки
#    Вставить цепочку: соревнование → протокол → категория → спортсмен → результат → подъёмы,
#    затем PRAGMA foreign_key_check — должен вернуть пусто.
#    Брать неудобный случай, а не простой: одноручный длинный цикл на 30 минут,
#    категорию «+95», зачёт новичков.

# 3. Демо-данные пересобираются
npm run demo:gen && npm run db:local

# 4. Сайт собирается на новых данных
npm run snapshot
```

Если менялись поля, которые показываются на страницах, откройте `dist/` в браузере
и посмотрите скриншот хотя бы страницы турнира и карточки спортсмена. Собранный HTML
без ошибок не значит, что колонка не уехала.

## Что обновить вместе со схемой

- `scripts/gen_demo.py` — если появилось поле, которое обязано быть заполненным;
- `src/queries.js` — если поле должно попадать на страницы;
- `docs/schema.md` — если решение неочевидно: почему индекс, а не `UNIQUE`; почему
  поле продублировано; чего в схеме намеренно нет;
- `docs/decisions.md` — если правка меняет принятое решение, а не уточняет его;
- `CLAUDE.md` — если появился новый инвариант, который легко нарушить.

## Демо-данные

Генератор детерминирован: `npm run demo:gen` на тех же входных данных даёт тот же файл,
поэтому диффы в `seeds/0002_demo.sql` читаемы. Если диff выглядит как полная
перетасовка — вы случайно изменили порядок генерации, и это стоит починить, а не
закоммитить.

Демо-данные обязаны покрывать неудобные случаи, иначе они бесполезны: одноручные
дисциплины, полумарафон, зачёты любителей и новичков, категория с «+», отложенная
эстафета, спортсмены с несколькими выступлениями в одной серии, протокол с открытыми
проблемами. Добавляя поле, добавьте в демо и случай, где оно заполнено нетривиально.

Данные вымышленные. Не подставлять имена реальных спортсменов.
