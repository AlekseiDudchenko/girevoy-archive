# Изменение схемы

Схема живёт в `migrations/`, пояснения к неочевидным местам — в `docs/schema.md`,
решения, из которых она следует, — в `docs/decisions.md`. Правка схемы почти всегда
тянет за собой сиды протоколов и снимок сайта: пропустить эти шаги значит оставить
репозиторий в состоянии, где `npm run preview` падает.

## Сначала проверить, правда ли нужна новая сущность

Частая ошибка в этом проекте — заводить строку справочника под каждое сочетание
условий. Прежде чем добавлять таблицу или значение в справочник, проверьте по
`CLAUDE.md`, не является ли это параметром существующей сущности:

- новый вариант дисциплины («одной рукой», «30 минут», «полумарафон») — это
  `hands` и `time_limit_min` в `categories`, а не строка в `disciplines`;
- новый набор весовых категорий — ничего не требует, они хранятся как в протоколе;
- новый зачёт по уровню — строка в `divisions`.

Если сущность всё-таки нужна, продолжайте.

## Исторические данные не хранить в карточке сущности

Если значение может меняться от протокола к протоколу, поле на `athletes`, `persons`,
`clubs` или другой общей сущности не является источником истории. Оно максимум может
быть кэшем или «последним известным значением».

Примеры:

- тренер спортсмена;
- клуб и регион в конкретном старте;
- спортивный разряд на дату соревнования;
- должность спортивного деятеля во времени.

Для таких фактов обязательно сохранять provenance: связь с конкретным результатом,
соревнованием, протоколом или диапазоном дат. Агрегат вида «последний год» считать
из этих строк, а не из текущего состояния карточки.

Конкретно для тренеров:

- `person_coach_athletes` означает «когда-либо был указан тренером»;
- `person_coach_mentions` хранит фактическое упоминание тренера у спортсмена на
  конкретном соревновании;
- источник для этой истории — `data/*.json`; `athletes.coach` нельзя использовать
  для восстановления прошлых лет;
- `scripts/gen_people.py` должен пересобирать связи после изменения протоколов.

Если новая фича отвечает на вопрос «когда это было?», а схема не хранит ссылку на
источник или дату, считать модель незавершённой.

## Куда писать миграцию

Пока схема не применена ни на одной живой базе (`wrangler d1 execute` не запускался
на боевой), правьте `0001_init.sql` на месте — это честнее, чем цепочка миграций,
из которых половина отменяет предыдущую.

Как только база развёрнута, только новый файл: `migrations/0002_<что_меняется>.sql`.
SQLite не умеет менять и удалять колонки произвольно, поэтому перенос данных пишется
через создание новой таблицы, `INSERT ... SELECT` и переименование.

## Проверка

Выполнять целиком, не выборочно. Первые две проверки ловят почти всё.

```sh
# 1. Схема выполняется на чистой базе
python3 - <<'PY'
import sqlite3
c = sqlite3.connect(':memory:')
for f in ('migrations/0001_init.sql', 'migrations/0002_people.sql'):
    c.executescript(open(f, encoding='utf-8').read())
print('схема ок')
PY

# 2. Схема принимает связанные записи и не рвёт ссылки
#    Вставить цепочку: соревнование → протокол → категория → спортсмен → результат → подъёмы,
#    затем PRAGMA foreign_key_check — должен вернуть пусто.
#    Брать неудобный случай, а не простой: одноручный длинный цикл на 30 минут,
#    категорию «+95», зачёт новичков.

# 3. Сиды пересобираются, включая производные данные персон
npm run seed:gen
npm run people:gen
npm run db:local

# 4. Тесты модели персон проходят
node --test tests/people.test.mjs

# 5. Сайт собирается на новых данных
npm run snapshot
```

Если менялись поля, которые показываются на страницах, откройте `dist/` в браузере
и посмотрите скриншот хотя бы страницы турнира и карточки спортсмена. Собранный HTML
без ошибок не значит, что колонка не уехала.

## Что обновить вместе со схемой

- `scripts/gen_seed.py` и `data/*.json` — если появилось поле, которое обязано
  быть заполненным: сначала в JSON, потом `npm run seed:gen`;
- `scripts/gen_people.py` — если меняется модель персон, ролей или тренерских связей;
- `src/queries.js` — если поле должно попадать на страницы;
- `docs/schema.md` — если решение неочевидно: почему индекс, а не `UNIQUE`; почему
  поле продублировано; чего в схеме намеренно нет;
- `docs/decisions.md` — если правка меняет принятое решение, а не уточняет его;
- `CLAUDE.md` — раздел «Схема» (карта таблиц) и список инвариантов, если появился новый.

## Сиды протоколов

Источник правды — `data/<slug>.json`, SQL из него собирает `npm run seed:gen`.
Править `seeds/*.sql` руками нельзя: следующая генерация затрёт правку.

Производные связи персон тоже не правятся вручную: `scripts/gen_people.py` читает
те же `data/*.json` и строит SQL во временный `.local/people.sql`. Это особенно важно
для истории тренеров: значение должно оставаться привязанным к соревнованию, где оно
напечатано.

Генераторы должны быть детерминированными. Если дифф выглядит как полная перетасовка,
изменился порядок генерации, и это стоит починить, а не закоммитить.

Демо-данных в репозитории нет: в базе только реальные протоколы. Проверять новое поле
надо на них, а не на выдуманной строке — вымышленный спортсмен в этой базе читается
как утверждение о реальном человеке. Если ни один протокол не покрывает нужный случай
(одноручные дисциплины, полумарафон, зачёты любителей, протокол с открытыми
проблемами), это довод оцифровать подходящий протокол, а не сочинить данные.
