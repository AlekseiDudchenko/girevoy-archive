# Ошибки в протоколах

Этот skill применяется, когда установлено, что **ошибка находится в первоисточнике**, а не
возникла при OCR, ручном переносе или генерации базы.

## Главный принцип

**Источник не переписывается молча.**

Если в протоколе напечатано ошибочное значение, архив может использовать исправленное
значение для нормализованных данных, но обязан сохранить:

1. исходное значение;
2. исправленное значение;
3. область действия исправления;
4. основание исправления;
5. публичный след, который отображается в UI.

Для этого использовать существующий механизм:

```text
data/*.json warnings
        ↓
source_error_correction
        ↓
scripts/gen_corrections.py
        ↓
edits.changed_by = source_correction:<id>
        ↓
src/corrections.js
        ↓
src/correction-ui.js
```

Не создавать параллельный механизм ошибок без необходимости.

## 1. Сначала определить тип проблемы

Разделять три случая.

### A. Ошибка извлечения архива

Пример: OCR прочитал `32` вместо `24`, хотя в оригинале ясно напечатано `24`.

Это **не source correction**.

Нужно исправить JSON/импорт так, чтобы он совпадал с оригиналом. В `ERRATA.md` такую
ошибку можно отметить только как исправленную техническую ошибку архива, если это
важно для истории проекта.

### B. Ошибка самого протокола

Пример: в протоколе напечатано `32 кг`, но другие строки/разделы того же официального
протокола и подтверждающие источники однозначно показывают, что должно быть `24 кг`.

Это `source_error_correction`.

Исправление должно быть публичным и отображаться в UI.

### C. Неоднозначность

Если есть только подозрение, а доказательства недостаточны, ничего не исправлять.
Сохранить исходное значение и записать находку в `ERRATA.md` как требующую проверки.

## 2. Где хранится публичное исправление

Публичные source corrections задаются в соответствующем `data/*.json` через
`warnings`.

Минимальная форма:

```json
{
  "id": "unique-correction-id",
  "type": "source_error_correction",
  "public": true,
  "correction_applied": true,
  "field": "bell_kg",
  "source_value": 32,
  "corrected_value": 24,
  "scope": {
    "discipline": "snatch",
    "sex": "f",
    "weight_classes": ["63", "68", "68+"]
  }
}
```

`id` должен быть устойчивым и уникальным. Предпочтительно включать slug турнира и
суть исправления.

Не редактировать производный SQL вручную. Его создаёт
`scripts/gen_corrections.py`.

## 3. Поддерживаемые области исправления

Генератор умеет применять исправление на уровнях:

- `competition`;
- `category`;
- `athlete`;
- `result`.

Если `entity` не указан, он выводится из `field`.

### Поля категории

В частности:

- `bell_kg`;
- `hands`;
- `time_limit_min`;
- `weight_class_raw`;
- `weight_class_kg`;
- `weight_class_is_open`;
- `sex`;
- `age_group_id`;
- `division_id`;
- `discipline_id`.

### Поля спортсмена

В частности:

- `birth_year`;
- `last_name`;
- `first_name`;
- `middle_name`;
- `region_id`;
- `club_id`;
- `coach`;
- `sport_rank_id`.

### Поля соревнования

В частности:

- `name`;
- `date_start`;
- `date_end`;
- `city`;
- `country`;
- `federation_id`.

Остальные поля по умолчанию считаются исправлениями результата.

Если новый тип исправления не поддерживается, сначала изменить
`scripts/gen_corrections.py` и тесты.

## 4. Scope должен быть максимально узким

Исправление не должно затрагивать больше строк, чем доказано.

Использовать подходящие фильтры:

- `discipline`;
- `sex`;
- `weight_class` / `weight_classes`;
- `hands`;
- `time_limit_min`;
- `bell_kg`;
- `athlete` / `athletes`;
- `places`;
- `source_pages`;
- `result_ids`.

Если можно указать одного спортсмена вместо всей категории — указывать одного
спортсмена.

Перед merge PR убедиться, что сгенерированный SQL выбирает ожидаемое количество
сущностей.

## 5. ERRATA.md обязателен для подтверждённых ошибок источника

Подтверждённую ошибку первоисточника описывать в `ERRATA.md`.

Указать:

- что ошибочно;
- соревнование и категорию;
- страницу/лист источника, если известно;
- исходное значение;
- почему оно признано ошибочным;
- какое значение используется архивом;
- выполнено ли публичное исправление.

`ERRATA.md` — человеческий аудит, а `source_error_correction` — машиночитаемая
реализация. Одно не заменяет другое.

Не добавлять в ERRATA обычные варианты форматирования, если они не являются ошибкой.

## 6. Merge спортсменов и correction — разные решения

**Merge отвечает на вопрос: "это один и тот же человек?"**

**Correction отвечает на вопрос: "какое значение первоисточника ошибочно?"**

Эти операции нельзя смешивать.

### Пример: опечатка в отчестве

В источнике:

```text
Васин Артём Иывнович, 2007
```

Каноническая персона:

```text
Васин Артём Иванович, 2007
```

Если доказано, что это один человек:

1. добавить merge в `data/merges.json`;
2. оставить старую запись спортсмена в базе через `merged_into_id`;
3. сохранить исходное написание в `results.raw_name`;
4. добавить публичный athlete correction:
   `middle_name: Иывнович → Иванович`;
5. описать ошибку в `ERRATA.md`.

Тогда UI показывает исправление, а старые slug продолжают работать.

### Пример: отчество отсутствует

```text
Иванов Иван, 1990
Иванов Иван Сергеевич, 1990
```

Если идентичность подтверждена, merge допустим.

Но отсутствие отчества само по себе **не является ошибкой протокола**. Не создавать
`source_error_correction` только ради merge.

## 7. Как находить дубли спортсменов

Поиск дублей делать отдельно от обычного импорта. Цель — найти **кандидатов**, а не
автоматически объединить похожие записи.

### 7.1. Начать с точных и почти точных совпадений

Искать пары/группы по убыванию надёжности:

1. одинаковые фамилия + имя + год рождения;
2. одинаковое полное ФИО + год рождения;
3. одинаковые фамилия + имя + год, но в одной записи нет отчества;
4. одинаковые фамилия + имя, отчества отличаются на 1–2 символа;
5. одинаковые ФИО, но год рождения отличается на 1 год или явно выглядит как опечатка;
6. близкие ФИО по Levenshtein/Jaro-Winkler при совпадении дополнительных признаков.

Перед fuzzy-поиском нормализовать строки только для сравнения:

- trim;
- несколько пробелов → один;
- `ё → е`;
- привести регистр;
- нормализовать дефисы;
- убрать точки и лишние пробелы в инициалах.

Эта нормализация **не меняет raw-данные**.

### 7.2. Дополнительные признаки одного человека

Для каждой пары кандидатов сравнить:

- год рождения;
- регион;
- клуб;
- тренеров;
- пол;
- весовые категории;
- соревнования и годы выступлений;
- историю результатов;
- raw-name во всех протоколах;
- старые slug;
- наличие одной и той же роли тренера/судьи/спортсмена.

Особенно сильные признаки:

- один вариант без отчества, другой с отчеством;
- одинаковый год рождения;
- один и тот же регион/клуб;
- последовательная спортивная история без конфликтов;
- одна запись заканчивается там, где начинается другая после изменения написания.

### 7.3. Красные флаги против merge

Не объединять, если найдено хотя бы одно сильное противоречие:

- обе записи участвуют в одной категории одного соревнования как два разных человека;
- устойчиво разные годы рождения в нескольких независимых источниках;
- разные полы;
- несовместимые одновременно существующие спортивные истории;
- разные регионы/клубы сами по себе не запрещают merge, но требуют дополнительной
  проверки;
- одинаковые фамилия и имя без других совпадений недостаточны.

Если есть сомнение — оставить записи раздельными.

### 7.4. Классификация кандидатов

Каждую найденную пару классифицировать:

#### `SAFE_MERGE`

Есть достаточные основания считать записи одним человеком.

Типичные случаи:

- ФИО + год совпадают, одна запись без отчества;
- опечатка в одной букве отчества, год/регион/история совпадают;
- различается только регистр или форматирование;
- ошибка года рождения подтверждена несколькими другими протоколами.

#### `REVIEW`

Похоже на одного человека, но есть конфликт:

- разные годы рождения;
- заметно различающееся отчество;
- нет достаточной истории;
- совпадает только часть дополнительных признаков.

Не мержить автоматически.

#### `KEEP_SEPARATE`

Есть доказательство, что это разные люди.

### 7.5. Не использовать один similarity score как решение

Можно использовать score только для сортировки кандидатов, например:

```text
surname exact        +40
first name exact     +30
birth year exact     +50
middle name exact    +20
surname edit dist 1  +25
first name dist 1    +20
region exact         +10
club exact           +10
coach overlap        +10
```

Но итоговый merge должен приниматься по конкретным фактам. Высокий score не заменяет
проверку конфликтов.

### 7.6. Практический аудит базы

При полном поиске дублей идти пакетами:

1. фамилия + имя + год рождения;
2. полное ФИО;
3. записи без отчества;
4. опечатки в отчестве;
5. опечатки в имени/фамилии;
6. конфликтующие годы рождения;
7. уже существующие merge — проверить на ложные объединения.

Для каждой пары выводить минимум:

```text
candidate A: id, ФИО, год
candidate B: id, ФИО, год
общие признаки
противоречия
соревнования обеих записей
решение: SAFE_MERGE / REVIEW / KEEP_SEPARATE
```

## 8. Как мержить подтверждённых дублей

Merge делать только через существующий механизм `data/merges.json`.

Пример:

```json
{
  "canonical": "Иванов Иван Сергеевич",
  "duplicate": "Иванов Иван",
  "birth_year": 1990,
  "reason": "Совпадают фамилия, имя, год рождения, регион и история выступлений; в старом протоколе отчество отсутствует."
}
```

### 8.1. Как выбрать canonical

Предпочитать запись:

1. с корректным подтверждённым написанием ФИО;
2. с более полным ФИО;
3. с правильным годом рождения;
4. уже имеющую больше связанных результатов/slug, если остальные признаки равны.

Не выбирать canonical только по меньшему ID.

### 8.2. Что происходит после merge

Ожидаемая модель:

```text
duplicate athlete
    merged_into_id
          ↓
canonical athlete
```

При этом:

- duplicate row остаётся в `athletes`;
- старые результаты сохраняют исходный `athlete_id`;
- `getAthlete()` собирает результаты canonical + duplicate;
- старые `athlete_slugs` продолжают вести на canonical;
- `results.raw_name` сохраняет исходное написание;
- список спортсменов и статистика должны считать только canonical записи.

Не перепривязывать вручную каждый `result.athlete_id`, если текущий механизм этого
не требует.

### 8.3. Merge при ошибке ФИО

Если duplicate появился из-за подтверждённой ошибки самого протокола:

1. сделать merge;
2. добавить athlete-level `source_error_correction`;
3. добавить запись в `ERRATA.md`;
4. проверить correction marker в UI.

Если различие вызвано только отсутствующим отчеством или допустимым сокращением,
correction не нужен.

### 8.4. Merge при ошибке года рождения

Если один и тот же спортсмен разделился из-за разного года рождения:

- сначала доказать правильный год по независимым протоколам;
- merge хранить отдельно в `data/merges.json`;
- неверный год оформить как athlete `source_error_correction`;
- не менять raw-значение источника молча.

### 8.5. Проверки после merge

После изменения `data/merges.json` обязательно проверить:

- duplicate действительно существует;
- canonical действительно существует;
- duplicate не уже merged в другого спортсмена;
- нет цепочки/цикла `A → B → A`;
- старый slug открывает canonical;
- карточка canonical содержит результаты обеих записей;
- duplicate исчез из обычного списка спортсменов как отдельная персона;
- количество результатов не изменилось;
- raw_name не потерян;
- corrections продолжают наследоваться через canonical id.

Технические проверки:

```sh
npm run people:gen
npm run db:local
node --test tests/people.test.mjs tests/corrections.test.mjs
node --test tests/*.test.mjs
```

И:

```sql
PRAGMA foreign_key_check;
```

Если есть отдельный генератор merges, запускать его согласно текущему `package.json`
или pipeline проекта; производный SQL руками не править.

### 8.6. Массовые merge

Даже если найдено много очевидных дублей:

- не применять fuzzy-merge ко всей базе автоматически;
- группировать только подтверждённые `SAFE_MERGE`;
- спорные случаи оставлять в `REVIEW`;
- перед commit просматривать diff `data/merges.json`;
- после генерации проверять, что число canonical athletes уменьшилось ровно на число
  новых merge, а число результатов осталось тем же.

## 7. Старую запись спортсмена после merge не удалять

Для подтверждённых дублей использовать существующий механизм:

```text
athletes.merged_into_id
data/merges.json
scripts/gen_merges.py
athlete_slugs
```

Правила:

- duplicate остаётся в `athletes`;
- `merged_into_id` указывает на canonical;
- старые slug должны продолжать открывать каноническую карточку;
- raw results не перепривязывать вручную без необходимости;
- карточка канонического спортсмена должна собирать результаты обоих id;
- merge должен оставаться обратимым.

Не удалять duplicate row ради "чистой" базы.

## 8. Алиасы ФИО

Отдельную таблицу aliases для спортсменов не создавать без нового требования.

Источником фактических вариантов написания является:

```text
results.raw_name
```

`getAthlete()` уже собирает отличающиеся варианты и показывает их как
`other_spellings` / «В протоколах также».

Важно:

- alias не означает ошибку;
- source correction означает подтверждённую ошибку;
- merge означает идентичность человека.

Один raw alias может быть корректным сокращением и не требовать correction.

## 9. Как correction наследуется после merge

`src/corrections.js` разрешает merged athlete к каноническому id.

Поэтому athlete-level correction канонического спортсмена должен отображаться для
результатов:

- canonical athlete id;
- historical duplicate athlete ids, которые ведут на canonical.

Это обязательное поведение. Не дублировать одну и ту же correction для каждого
duplicate вручную.

## 10. UI

Публичные исправления должны отображаться через существующий
`src/correction-ui.js`.

UI показывает маркер исправления и tooltip вида:

```text
Исправлено в архиве
Вес гири: 32 кг → 24 кг
```

Для ФИО и других новых полей при необходимости добавить понятную подпись в
`FIELD_LABELS`.

Исправление должно быть видно везде, где показывается затронутая запись, если это
поддерживает текущая страница:

- страница соревнования;
- «Все результаты»;
- карточка спортсмена;
- другие таблицы, использующие corrections.

Нельзя считать задачу завершённой, если correction существует в БД, но теряется в
одном из основных UI-представлений.

## 11. Проверки перед PR

Минимум выполнить:

```sh
python3 scripts/gen_corrections.py data/*.json > /tmp/corrections.sql
node --test tests/corrections.test.mjs
```

Если менялся merge спортсменов:

```sh
npm run people:gen
npm run db:local
node --test tests/people.test.mjs tests/corrections.test.mjs
```

Также проверить:

```sql
PRAGMA foreign_key_check;
```

Если изменение влияет на сайт, желательно выполнить полный тестовый набор:

```sh
node --test tests/*.test.mjs
```

## 12. Что проверить в сгенерированном correction SQL

Проверить вручную:

- правильный `entity`;
- правильный `entity_id`/target;
- правильный `field`;
- `old_value` = реально напечатанному источнику;
- `new_value` = подтверждённому исправлению;
- `changed_by = source_correction:<id>`;
- scope не захватывает соседние категории/спортсменов.

Для athlete corrections target должен разрешаться к канонической записи через
`COALESCE(a.merged_into_id, a.id)`.

## 13. Работа через PR

Все изменения ошибок делать только:

```text
fresh main
  ↓
отдельная ветка
  ↓
изменения
  ↓
тесты
  ↓
PR
  ↓
review diff
  ↓
CI green
  ↓
merge
```

Никогда не коммитить исправление напрямую в `main`.

Перед merge:

1. получить свежий SHA `main`;
2. проверить, что PR не содержит чужих/случайных изменений;
3. проверить mergeability;
4. проверить обязательные CI runs для head SHA;
5. если другой агент изменил те же данные — пересобрать ветку на свежем состоянии.

## 14. Чек-лист подтверждённой ошибки ФИО

Для опечатки в имени/фамилии/отчестве:

- [ ] сверить оригинальный протокол;
- [ ] определить каноническое написание по независимым данным;
- [ ] решить отдельно, нужен ли merge;
- [ ] если нужен — добавить `data/merges.json`;
- [ ] не удалять duplicate athlete;

## 16. Запрещённые упрощения

Не делать:

- молчаливое исправление JSON без public correction, если ошибка была в источнике;
- merge только потому, что ФИО похожи;
- correction только потому, что записи были merged;
- удаление duplicate athlete после merge;
- отдельный список aliases, дублирующий `results.raw_name`;
- ручное редактирование производных SQL-файлов;
- correction с широким scope «на всякий случай»;
- автоматическую замену всех похожих опечаток в других турнирах без проверки каждого
  источника;
- merge PR с красным CI.
