# Аудит персон

Полный аудит можно запускать **отдельно от protocol-import**, но правила сопоставления
из этого skill используются и во время импорта: перед финализацией нового протокола
входящих спортсменов и тренеров нужно проверить против уже существующих персон и вынести
неоднозначные совпадения на review.

## Главный принцип

**Не исправлять данные протокола. Исправлять только модель идентичности персон и
производные связи, когда есть достаточные основания.**

Одинаковые или похожие ФИО не означают автоматически одного человека. Разные написания
не означают автоматически разных людей.

По умолчанию аудит:

1. находит кандидатов на проблему;
2. собирает подтверждающие данные из всех протоколов;
3. классифицирует уверенность;
4. предлагает действие;
5. ничего не сливает автоматически без явного указания администратора.

## Источники правды

Для аудита использовать в первую очередь:

- `data/*.json` и `data/categories/**/*.json` — сырые значения из протоколов;
- `scripts/gen_people.py` — правила построения персон и тренерских связей;
- `data/merges.json` и `scripts/gen_merges.py` — уже подтверждённые объединения;
- локальную БД после `npm run db:local` — для поиска дублей и проверки связей;
- `person_coach_mentions` — история упоминаний тренера в конкретных соревнованиях;
- `person_coach_athletes` — агрегированная связь «когда-либо был тренером».

Не использовать `athletes.coach` как источник исторической истины о тренерах.

### Нормализация регионов при сопоставлении

Регион — подтверждающий признак идентичности, поэтому перед сравнением его нужно
нормализовать. Различие только в сокращении типа области **не считается конфликтом**.

Обязательное правило для всех областей России:

- `Томская обл.` = `Томская область`;
- `Омская обл` = `Омская область`;
- в общем случае `<Название> обл.`, `<Название> обл` и
  `<Название> область` — одно и то же каноническое значение
  `<Название> область`.

При таком сравнении можно игнорировать регистр, лишние пробелы и точку после
`обл`. Это **не ошибка источника и не ERRATA**.

Нормализация используется только для поиска/сопоставления персон. Сырое значение региона
в протоколе не переписывать. Действительно разные субъекты РФ не объединять по
приблизительному сходству названий.

## 1. Сначала собрать кандидатов на дубли спортсменов

Искать группы с похожими признаками:

- одинаковые фамилия + имя + год рождения;
- одинаковое полное ФИО при разных athlete/person id;
- одинаковые фамилия + имя, но один источник без отчества;
- одинаковое ФИО при отличающемся только формате даты рождения;
- близкие варианты ФИО, отличающиеся одной буквой, и совпадающие по году рождения,
  региону, клубу или тренеру;
- несколько slug, ведущих на людей с практически одинаковой историей выступлений.

Не считать совпадение фамилии, региона или тренера достаточным основанием для merge.

## 2. Классифицировать кандидатов

Для каждой пары/группы определить один из статусов:

### `SAFE_MERGE`

Есть сильные независимые признаки, что это один человек. Например:

- совпадают фамилия, имя и год рождения;
- в одном источнике есть отчество, в другом оно отсутствует;
- совпадают регион/клуб и история выступлений;
- нет противоречащих фактов.

### `REVIEW`

Есть существенные основания считать людей одинаковыми, но остаётся неоднозначность.
Например:

- совпадают ФИО, но год рождения отличается;
- совпадает имя и история соревнований, но есть различия в регионе;
- возможна опечатка в имени или отчестве.

### `KEEP_SEPARATE`

Есть доказательство, что это разные люди. Например:

- они выступают в одной категории одного соревнования как разные участники;
- устойчиво различаются годы рождения при полном ФИО;
- одновременно имеют разные результаты/роли, несовместимые с одним человеком.

### `INSUFFICIENT_DATA`

Данных недостаточно. Ничего не менять.

## 3. Проверить ошибочные merge

Проверять не только недостающие объединения, но и уже существующие merge.

Красные флаги:

- объединённая персона одновременно присутствует дважды в одной категории;
- у объединённых спортсменов несовместимые годы рождения;
- один merge соединяет разные полные ФИО без понятного объяснения;
- после merge теряется отдельная спортивная история;
- slug одного человека неожиданно ведёт на явно другого.

Если существующий merge выглядит ошибочным, не переписывать историю автоматически.
Сначала собрать конкретные протоколы и показать причину конфликта.

## 4. Аудит ролей персоны

Проверить, что роли объединяются в одну `person`, а не создают параллельных людей:

- спортсмен;
- тренер;
- судья;
- спортивный деятель.

Если один и тот же человек встречается в нескольких ролях, его карточка должна быть
одной, а разделы ролей — отдельными.

Не объединять роли только по фамилии и инициалам.

## 5. Аудит тренеров

Для тренеров проверить:

- несколько тренеров в одной raw-строке не были ошибочно склеены в одного;
- один и тот же тренер не размножился из-за вариантов `Иванов И.И.` / `Иванов И. И.`;
- тренер, который также является спортсменом/судьёй/деятелем, привязан к той же person,
  если идентичность подтверждена;
- неоднозначные инициалы не привели к ложному merge.

Raw-текст тренера из протокола не переписывать.

## 6. Проверить историю тренерских связей

`person_coach_mentions` должен быть источником истории.

Проверить:

- каждое упоминание связано с конкретным соревнованием;
- старый протокол не уменьшает `last_seen_year`;
- отсутствие тренера в более новом протоколе не удаляет старую связь;
- `last_seen_year` = максимальный год оцифрованного соревнования, где эта связь
  действительно напечатана;
- `person_coach_athletes` соответствует агрегату из mentions.

Если агрегат расходится с mentions — чинить генерацию, а не вручную редактировать
производную таблицу.

## 7. Что не является ошибкой аудита

Не считать проблемой персон само по себе:

- изменение клуба;
- изменение региона;
- отличие только в форме `обл.` / `область` для одного и того же региона;
- изменение спортивного разряда;
- смену тренера;
- отсутствие отчества в одном из протоколов;
- различное форматирование ФИО;
- ошибку или опечатку, напечатанную в самом протоколе.

Такие различия важны только как признаки при идентификации человека.

## 8. Минимальные технические проверки

Перед аудитом собрать актуальную локальную БД:

```sh
npm run db:local
```

После любых подтверждённых изменений персон/merge:

```sh
npm run people:gen
npm run db:local
node --test tests/people.test.mjs
```

и проверить:

```sql
PRAGMA foreign_key_check;
```

Если менялся генератор, дополнительно убедиться, что повторный запуск детерминирован и
не создаёт неожиданный большой diff.

## 9. Формат результата аудита

Итог выдавать коротким списком кандидатов:

```text
SAFE_MERGE
- Иванов Иван, 1990: athlete 123 + 487
  Причина: совпадают имя, год, регион; в одном протоколе отсутствует отчество.

REVIEW
- Петров Алексей Сергеевич: athlete 55 + 901
  Причина: совпадает ФИО, но год рождения 1988 / 1989.

KEEP_SEPARATE
- Сидоров Павел, 1992: athlete 31 + 44
  Причина: оба выступают в одной категории одного турнира.
```

Для каждого кандидата указывать конкретное основание, а не только similarity score.

## 10. Изменения после аудита

Если администратор просит применить подтверждённые исправления:

- подтверждённые merge хранить через существующий механизм `data/merges.json`;
- производные SQL руками не править;
- после изменения пересобрать merges/people/локальную БД;
- проверить slug и публичную карточку объединённой персоны;
- не менять raw-значения результатов протоколов ради красивой карточки человека.

Если уверенности недостаточно — оставить людей раздельными. Ложный дубль безопаснее
ложного объединения, потому что merge смешивает историю двух реальных людей.

## 11. Массовый аудит

При полном аудите базы работать пакетами:

1. точные совпадения ФИО + год;
2. источники без отчества;
3. варианты форматирования/инициалов;
4. подозрительные близкие ФИО;
5. проверка уже существующих merge;
6. тренеры и роли;
7. история `last_seen_year`.

Не останавливать весь аудит из-за одного спорного человека. Спорного кандидата пометить
`REVIEW` и продолжить со следующими.
